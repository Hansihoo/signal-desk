## MCP Apps: AI가 찾은 공고를 대화 안에서 비교하고 선택하기

### 비교할 정보가 많아지면 텍스트 대화만으로는 번거롭다

AI에게 ‘이번 달에 신청할 수 있는 공고를 찾아줘’라고 묻는 상황을 생각해 보자.
AI가 공고 세 개의 제목과 마감일을 문장으로 답했다. 조건을 비교하려면
위아래를 다시 읽어야 하고, 상세 내용을 보려면 공고 이름을 다시 적어야 한다.
답을 받았지만 비교와 선택에는 여전히 여러 번의 대화가 필요하다.

같은 결과를 표로 볼 수 있다면 제목·마감일·지역을 나란히 확인하고 원하는
행을 선택할 수 있다. MCP Apps는 MCP 도구와 이런 조작 가능한 화면을
연결하는 확장이다. 사용자는 Apps를 지원하는 AI 앱 안에서 화면을 보고
조작한다. 개발자는 업무 데이터를 만드는 기능과 데이터를 표현할 HTML을
연결해 제공한다. [공식 개요](https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html)

여기서 필요한 것은 ‘AI가 더 긴 답을 쓰게 하는 기능’보다 사람이 정보를
비교하고 선택할 방법이다. 두세 줄의 공지를 읽는 일에는 텍스트가 충분할 수
있지만, 같은 목록의 조건을 바꾸고 상세 조회를 반복한다면 화면이 유용할 수
있다. 이 도입 판단은 아래 가상 사례를 바탕으로 한 편집 의견이다.

### 먼저 정보를 가져오는 기능과 AI 앱을 구분한다

MCP는 AI 앱이 외부 프로그램의 기능과 자료를 이용하도록 요청과 결과를
주고받는 규칙이다. 공고를 검색하는 프로그램이 이름·입력 형식·결과를
공통 규칙으로 제공하면 AI 앱이 그 기능을 찾아 호출할 수 있다.

공고 데이터를 보유하고 검색하는 프로그램을 **MCP 서버**라고 한다. 서버는
프로그램의 역할을 가리키므로 반드시 별도 클라우드 컴퓨터를 의미하지 않는다.
사람이 대화하는 AI 앱은 **호스트**다. 호스트 안의 **MCP 클라이언트**는 서버와
연결해 요청과 응답을 주고받는 구성 요소다.
[공식 MCP 구조](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

공고 검색을 연결했다고 해서 AI 모델이 원래 모든 공고를 알고 있는 것은
아니다. 검색 기능이 데이터를 반환하고, 모델은 전달받은 결과로 답을 만든다.
이 둘을 구분해야 오래된 답변을 고칠 때 검색 자료를 바꿔야 하는지, 설명을
만드는 방식을 바꿔야 하는지 판단할 수 있다.

### ‘B 상세보기’를 누르면 어디에서 무슨 일이 일어날까

아래는 공고 A·B·C가 있다는 가상 사례다. 설명을 따라가기 위한 자료이며
실제 지원 공고가 아니다. 검색 결과에는 각 공고의 식별자·제목·마감일이 있다.
식별자는 제목이 비슷해도 정확히 어느 공고를 선택했는지 지정하기 위한 값이다.

1. 사용자가 공고 검색을 요청한다. 호스트는 연결된 검색 도구를 통해 목록을 얻는다.
2. 검색 도구에는 목록을 표시할 화면 리소스의 주소가 연결되어 있다.
   서버는 HTML 화면을 제공하고 호스트는 그 자료를 읽는다.
3. 호스트는 대화 안의 격리된 화면에 HTML을 실행하고 검색 결과를 전달한다.
   이 실행된 화면을 **View**라고 한다. View는 받은 A·B·C 데이터를 표로 보여준다.
4. 사용자가 B 행의 ‘상세보기’를 누른다. View는 ‘B의 상세 데이터를 달라’는
   요청을 호스트에게 보낸다. 호스트는 서버의 상세 조회 도구에 요청을 전달한다.
5. 서버가 B의 상세 데이터를 반환한다. 호스트를 거쳐 결과를 받은 View가
   상세 내용을 표시한다. 새 정보를 만드는 곳은 서버의 조회 기능이고,
   그 정보를 보여주는 곳은 화면이다.

이 경로는 공식 Apps 사양의 도구 호출·결과 전달 구조를 설명용 공고 사례로
바꾼 것이다. 실제 구현에서는 지원 기능과 호출 가능한 도구를 확인해야 한다.
[공식 Apps 사양](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

### 데이터와 화면이 따로 있다는 말의 의미

공고 B의 제목과 마감일은 **업무 데이터**다. 어떤 순서로 행을 놓을지, 어느
버튼을 보여줄지 정하는 HTML은 **화면 리소스**다. 서버가 HTML 리소스를
제공하고 호스트가 읽어 표시한다. ‘서버가 읽을 수 있게 만든 화면’으로
기억하면 읽는 주체가 뒤바뀐다.
[UI 리소스 설명](https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html#ui-resources)

예를 들어 B의 마감일이 바뀌었다면 서버가 반환하는 데이터가 바뀌어야 한다.
표를 카드 목록으로 바꾸는 일은 표현 방식을 바꾸는 작업이다. 같은 업무 데이터를
카드로 보여줄 수 있도록 만들어 두었다면 데이터의 의미까지 다시 작성할 필요는
없다. 버튼을 누를 때마다 HTML 전체를 새 업무 데이터처럼 만들 이유도 없다.

### 클릭으로 화면이 바뀌는 것과 AI에게 선택을 알리는 것은 다르다

상세보기 버튼은 도구를 호출해 화면을 갱신할 수 있다. 그 클릭이 곧바로
‘AI가 B를 선택한 사실을 이해하고 답변까지 시작했다’는 뜻은 아니다.
선택한 값을 대화의 맥락에 넣거나 메시지를 보내는 동작은 별도로 연결한다.
Apps 사양은 `ui/update-model-context`와 `ui/message`를 구분한다. 문맥 갱신은
이후 대화에서 사용될 수 있고, 실제 처리 시점과 동작은 호스트에 따른다.
[공식 문맥·메시지 규정](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

따라서 ‘B의 상세 내용을 화면에서 읽기’와 ‘선택한 B를 AI에게 설명해 달라고
요청하기’는 같은 버튼처럼 보이더라도 서로 다른 업무다. 만들 기능을 정할 때
어느 결과를 원하는지 먼저 정해야 한다.

### 공식 시간 예제에서는 무엇을 관찰하면 될까

공식 Quickstart는 `get-time` 도구가 반환한 서버 시간을 화면에 표시한다.
버튼을 누르면 `app.callServerTool`로 같은 도구를 다시 요청하고 새 값을
표시한다. 화면은 결과를 받는 함수와 버튼 요청을 처리하는 함수를 따로 갖는다.
[공식 시간 예제](https://apps.extensions.modelcontextprotocol.io/api/documents/quickstart.html)

관찰할 것은 ‘버튼이 있다’는 사실보다 시간의 출처다. 화면의 숫자를 임의로
바꾸는 버튼과, 서버에서 새 값을 조회하는 버튼은 다르다. 연결 과정을 이해했다면
서버에서 만든 값이 요청을 거쳐 화면까지 오는 경로를 코드에서 찾을 수 있다.

구현으로 넘어가려면 기존 MCP 서버, Tools·Resources의 이해와 Node.js 20+
등 Quickstart의 준비 조건을 갖춰야 한다. 아직 그 준비가 없다면 먼저 서버가
도구를 제공하고 호스트가 호출하는 기본 왕복을 익힌 후 시간 예제로 이어간다.
공식 예제의 성공과 자신이 사용할 호스트에서의 동작도 별도로 확인한다.

### 어디에 쓰면 도움이 되는가

후보 비교, 필터 변경, 선택 후 상세 조회처럼 같은 자료를 반복해서 조작하는
일에 적용을 검토할 수 있다. 읽기만 하는 한 줄 답변이나 이미 쓰기 편한 외부
업무 화면에는 화면을 새로 만드는 비용에 비해 이점이 작을 수 있다.
이 판단은 기능의 성격에 대한 권고이며 생산성 향상을 측정한 결과는 아니다.

앱이 기본 MCP 도구를 연결할 수 있다는 것만으로 Apps 화면 지원까지 확보되는
것은 아니다. 도구의 기능과 화면의 지원 여부를 따로 확인한다. 공식 Apps는
지원되지 않는 호스트에서 텍스트 결과를 사용하는 방향도 설명한다.
[지원 협의](https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html#progressive-enhancement)

### 다른 사례에 적용해 보기

공고 대신 매출 표를 보여주는 화면이 있다고 가정하자. 사용자가 날짜를 바꿨는데
지난 기간의 숫자가 그대로 나타난다. 어디를 확인해야 할까?

먼저 변경한 날짜가 조회 도구의 입력까지 전달됐는지 보고, 서버 반환값이 새
기간의 데이터인지 확인한다. 반환값은 맞는데 화면만 옛 숫자라면 View의 결과
처리와 갱신을 살펴본다. 화면의 색이나 제목을 바꾸는 것만으로 조회 오류가
해결되지는 않는다. 입력·조회·반환·표시의 역할을 구분하면 어느 단계에서
문제가 생겼는지 좁힐 수 있다.

## 해커톤 기초: 도구 호출과 구조화 출력의 차이

### AI가 답을 만드는 것과 실제 목록을 조회하는 것

공고 앱에서 사용자가 ‘서울에서 10월 8일부터 31일까지 마감되는 공고를 찾아줘’라고
물었다. 원하는 결과는 그럴듯한 공고 이름이 아니라 저장된 자료에 실제로 있는
공고다. 모델이 질문을 해석하더라도 공고 자료를 읽는 기능은 따로 필요하다.

**도구 호출**에서는 모델이 사용할 함수 이름과 입력값을 제안한다. 앱은 그 값을
검사하고 함수를 실행한 뒤 반환값을 모델에 돌려준다. SDK가 일부 단계를 자동으로
연결하더라도 공고 자료를 실제로 읽는 함수와 그 입력·결과의 책임은 앱에 있다.
[공식 함수 호출 과정](https://ai.google.dev/gemini-api/docs/function-calling)

다음 예시는 이 왕복을 이해하기 위한 가상 데이터다. 특정 SDK의 실행 코드나
실제 모집 공고가 아니다. JSON은 필드 이름과 값을 묶어 프로그램끼리 정보를
주고받는 텍스트 형식이다. `region`은 지역, `from_date`와 `to_date`는 조회할
마감일 범위다. 날짜는 모두 이 예시의 같은 기준으로 비교한다.

### 날짜 조건을 실행 가능한 입력으로 만들기

앱이 제공할 조회 함수는 `find_notices(region, from_date, to_date)`다.
제목에 대한 설명만 제공했던 `find_notices(region, keyword)`에 날짜 조건을
추측해 맡기지 않는다. 개발자는 이 함수가 어디에서 자료를 읽고 어떤 범위의
날짜를 비교하는지 정한다.

모델이 제안할 입력을 단순한 객체로 표현하면 다음과 같다.

```json
{
  "region": "서울",
  "from_date": "2026-10-08",
  "to_date": "2026-10-31"
}
```

앱은 지원하는 지역인지, 날짜를 읽을 수 있는지, 시작일이 종료일보다 늦지
않은지 확인한다. 통과하면 조회 함수가 저장된 목록에서 조건에 맞는 자료를
찾는다. ‘이번 달’처럼 상대적인 날짜를 쓴 요청에서는 기준 날짜와 시간대를
정한 뒤 입력으로 바꿔야 한다.

아래 세 항목을 학습용 자료로 사용하자.

| ID | 제목 | 지역 | 마감일 | 자료 ID |
| --- | --- | --- | --- | --- |
| DEMO-A | 샘플 지원 A | 서울 | 2026-10-28 | DOC-A |
| DEMO-B | 샘플 지원 B | 경기 | 2026-10-20 | DOC-B |
| DEMO-C | 샘플 지원 C | 서울 | 2026-11-10 | DOC-C |

DEMO-A는 지역과 날짜가 모두 맞는다. DEMO-B는 날짜가 맞아도 지역이 다르며,
DEMO-C는 지역이 맞아도 날짜 범위를 벗어난다. 따라서 함수는 DEMO-A만
반환해야 한다. 반환에도 마감일과 자료 ID가 있어야 앱과 독자가 조건을 확인할 수 있다.

```json
{
  "items": [
    {
      "id": "DEMO-A",
      "title": "샘플 지원 A",
      "region": "서울",
      "deadline": "2026-10-28",
      "source_id": "DOC-A"
    }
  ]
}
```

### 조회 결과를 답변으로 바꾸기

앱이 이 반환값을 모델에 전달하면 모델은 ‘조건에 맞는 항목은 샘플 지원 A이고
마감일은 10월 28일’이라고 설명할 수 있다. DOC-A는 개발자가 실제 앱에서
원문 주소와 연결할 자료 식별자다. 이 가상 자료만으로 공식 신청 자격이나
지원 금액까지 답할 수는 없다. 그 질문에는 해당 내용을 가진 원문이 추가로 필요하다.

**구조화 출력**은 답변의 형식을 정하는 기능이다. 예를 들어 결과를 늘
`items` 배열과 `id`, `deadline`, `source_id` 필드로 받고 싶을 때 사용한다.
하지만 JSON 모양이 맞더라도 없는 공고 ID나 틀린 날짜를 넣을 수 있다.
그래서 반환된 ID가 조회 자료에 존재하고 값이 일치하는지 확인해야 한다.
[구조화 출력의 목적과 값 검증](https://ai.google.dev/gemini-api/docs/structured-output)

도구 호출은 자료를 가져올 행동을 연결하고, 구조화 출력은 앱이 사용할 최종
답의 모양을 정한다. 두 기능은 함께 쓸 수 있지만 같은 기능으로 보면
‘필드를 맞춰 받았으니 실제 검색도 성공했다’는 오해가 생긴다.

### 무엇을 보면 이해했거나 실패했는지 알 수 있을까

이 예시의 기대 결과는 DEMO-A 한 건이다. DEMO-B가 나오면 지역 조건을,
DEMO-C가 나오면 날짜 조건을 먼저 확인한다. 함수는 A만 반환했는데 최종
답에 C가 추가되었다면 검색 결과를 답변으로 바꾸는 단계에서 오류가 생겼다.
조회 오류가 발생했는데 ‘검색 결과가 없다’고 답하는 것도 실패다. 오류와
정상적으로 빈 목록을 얻은 결과를 구분해야 한다.

다른 질문을 해 보자. 날짜는 유지하고 지역만 경기로 바꾸면 어떤 결과가 나와야
할까? 기대 결과는 DEMO-B다. 서울의 A가 계속 나오면 입력 변경이 조회에
반영되지 않았을 수 있다. 이처럼 입력과 기대 결과를 함께 두면 어느 부분을
수정해야 하는지 설명할 수 있다.

기초 프로젝트에서는 이 왕복 하나를 만든 후 문서 본문 검색이나 음성을 추가하는
편이 이해하기 쉽다. 새 기능을 붙일 때에도 같은 질문·자료·기대 결과로 비교한다.
이 순서는 학습을 위한 권고이며 특정 대회의 필수 개발 순서가 아니다.

## A2A 연결 실습을 소개할 때 빠뜨리지 않을 설명

현재 글의 CLI 요청은 서버가 준비돼 있다는 조건에서 시작한다. 입문 실습으로
소개하려면 연결 확인용 echo 서버와 실제 문서 작업의 차이를 먼저 설명한다.
공식 안내의 echo 모드는 받은 문장을 그대로 돌려주는 학습·시험용 서버다.
[공식 CLI 실습](https://a2a-protocol.org/latest/blog/2026/10/01/introducing-a2a-cli/)

A2A CLI를 설치한 로컬 환경에서 두 터미널을 쓰는 공식 예시의 짧은 형태다.
이번 검토에서 명령을 실행한 것은 아니다.

```text
터미널 A: a2a server --echo --port 8080
터미널 B: a2a send -a http://localhost:8080 "hello"
예상 반환 내용: hello
```

입력과 같은 문장을 받았다면 통신 왕복을 확인한 것이다. 공고 조건을 비교하거나
문서를 요약한 것은 아니다. 연결에 성공한 다음에는 실제 처리 프로그램을
준비하고 그 프로그램의 입력·출력·실패를 같은 방식으로 설명해야 한다.
원격 AI를 연결한다는 말만으로 처리 능력이 생기는 것은 아니다.

## 작성자가 이 원고에서 재사용할 것

- 제목·요약을 줄이기 전에 독자의 문제와 필요한 개념의 관계를 먼저 쓴다.
- 약어 목록보다 한 장면의 요청·반환·표시를 유지한다.
- 입력·출력·필드·판정 이유를 맞춰 설명한다.
- 다른 입력의 기대 결과를 제시해 정의를 외운 것과 적용할 수 있는 것을 구분한다.
- 공식 기능, 개념용 예시, 실행 검증 결과를 섞지 않는다.

MCP 원고의 도달점은 새로운 화면에서 요청 경로를 설명하는 것이다. 도구 호출
원고의 도달점은 데이터 조회와 답변 형식을 구분하고, 틀린 결과가 어느 단계에서
나왔는지 찾는 것이다. 예시의 이해 질문은 편집상 점검이며 실제 독자 시험 결과는 아니다.
