# DevOps란? — 학습·팀 공유 HTML 제작 메모

작성일: 2026-10-10. 새 HTML을 함께 정하는 작업이다. 기존 페이지·공통 렌더러·발행 데이터는 수정하지 않는다. 사용자 피드백은 “레이아웃이 먼저고 전달 내용이 빈약하다”이며, 새 페이지의 목적은 자신이 먼저 공부하고 팀원에게 공유하는 것이다. 기존 판의 기술 검사나 에이전트 Pass를 이 요구의 수용 근거로 사용하지 않는다.

## 독자와 결과

- 독자는 코드를 작성하는 일을 알지만, 배포·운영·CI/CD의 관계는 모른다고 가정한다. 운영 담당자와 관리자도 읽을 수 있게 설명한다.
- 독자의 질문: “DevOps는 무엇이며, 우리 팀이 기능을 사용자에게 전달하고 장애에서 회복하는 과정에 어떻게 적용하는가?”
- 읽은 뒤 남길 결과물: 자기 팀의 변경 → 검증 → 배포 → 관찰 → 복구 흐름도와, 가장 먼저 고칠 병목 한 가지.
- 설명 중심의 입문 자료다. 실서버를 구축하는 실행 튜토리얼이나 특정 제품 도입 안내가 아니다.
- 선수 개념은 저장소/커밋 → 빌드 결과물 → 테스트 환경/운영 환경 → 배포/사용자 공개 → 운영 신호 순서로 소개한다.

## 제안한 화면과 선택 상태

HTML Design Helper의 원본 미리보기 절차에 따라 Quarto Book과 reveal.js 원본 화면을 제시했다. 후속 사용자가 **“둘다 만들어봐.”**라고 답했다. 따라서 같은 내용의 Quarto 장별 문서와 reveal.js 발표 자료를 모두 제작한다. 어느 쪽이 앞으로의 기본 형식인지는 아직 확정하지 않았다.

- Quarto Book: 왼쪽 장 목차, 가운데 연속 설명과 도표, 오른쪽 학습 과제 바로가기. 개인 학습과 다시 찾기에 적합하다는 제작자의 추천이다.

- 미리보기: `reports/devops-2026-10-10/choose-format.html`. 최종 DevOps 본문 HTML이 아니다.

## 본문 초안: 한 변경을 처음부터 끝까지 따라가기

아래는 화면에 넣을 내용을 먼저 검토하기 위한 원고다. 기술 설명과 명시된 가상 사례를 구분한다. 실제 앱 배포나 장애 실험은 수행하지 않았다.

### 1. 개발이 끝난 뒤에도 남아 있는 일

쇼핑 서비스의 무료배송 조건을 “3만 원 이상”에서 “2만 원 이상”으로 바꾼다고 생각해 보자. 코드 한 줄을 고쳤어도 고객은 아직 바뀐 서비스를 사용하지 못한다. 팀은 변경이 주문 금액 경계에서 제대로 작동하는지 검사하고, 실행할 버전을 만들고, 운영 환경에 전달해야 한다. 공개 후에는 주문이 정상 처리되는지 관찰하고 문제가 생기면 영향을 줄여야 한다. 이 글에서는 이 상황을 가상 사례로 끝까지 따라간다.

개발은 기능을 만드는 일이고 운영은 실제 사용자가 서비스를 계속 이용할 수 있게 하는 일이다. 개발팀이 “코드는 완성했다”고 넘기고 운영팀이 “변경은 위험하다”고 막는 구조에서는 사용자가 가치를 얻는 과정이 끊어지기 쉽다. **DevOps는 개발과 운영이 서비스의 전달과 안정성에 공동 책임을 지고, 작은 변경·자동화·빠른 피드백으로 일하는 문화와 실천의 묶음**이다. Dev는 Development, Ops는 Operations에서 왔다. 한 명이 모든 일을 맡거나 조직을 반드시 합쳐야 한다는 뜻으로 해석하지 않는다. [AWS 정의·협업 설명](https://aws.amazon.com/devops/what-is-devops/)

도해 1은 `변경 계획 → 코드 → 자동 검사 → 배포 준비 → 운영 배포 → 사용자 상태 관찰 → 다음 개선`으로 연결한다. 관찰에서 다음 변경으로 돌아오는 선을 분명히 그린다. 특정 제품 로고를 먼저 나열하지 않는다.

### 2. 코드, 실행할 버전, 공개는 서로 다른 상태다

저장소는 코드와 변경 이력을 함께 관리하는 장소다. 커밋은 그 이력에 기록한 변경 한 단위다. 빌드는 코드를 실행하거나 배포할 수 있는 형태로 준비하는 과정이고, 결과 파일이나 패키지를 빌드 결과물이라고 부른다. 모든 언어나 앱에 같은 컴파일 단계가 있는 것은 아니다. 테스트 환경은 사용자에게 공개하기 전에 점검하는 곳이고, 운영 환경은 실제 사용자의 요청을 처리하는 곳이다.

이 사례에서는 무료배송 변경을 기록한 커밋으로 `shop-v2` 결과물을 만든다. 테스트 환경에서 확인한 그 결과물을 운영 환경으로 옮긴다. **배포는 버전을 환경에 설치·적용하는 일이며, 사용자에게 기능을 공개하는 시점은 별도로 제어할 수도 있다.** 예를 들어 기능 스위치를 꺼 둔 채 새 코드를 배포한 후, 일부 사용자에게만 켤 수 있다. 빌드·배포·공개를 구분하면 “검사는 통과했는데 고객에게 아직 안 보인다”는 상태도 설명할 수 있다. [DORA 전달 과정](https://dora.dev/capabilities/continuous-delivery/), [Google SRE 기능 스위치 설명](https://sre.google/workbook/canarying-releases/)

### 3. CI와 두 가지 CD가 맡는 범위

CI(지속적 통합)는 개발자가 변경을 자주 합치고, 자동 빌드·테스트로 문제가 생겼는지 빠르게 확인하는 실천이다. 무료배송 예에서는 19,999원은 배송비가 붙고, 20,000원과 30,000원은 무료라는 경계 조건을 검사한다. 검사가 실패하면 변경을 고친다. CI가 초록색이라고 운영의 모든 상황이 안전하다고 결론 내리지는 않는다.

CD는 두 표현에 쓰여 구분이 필요하다. Continuous Delivery(지속적 전달)는 검증한 변경을 필요할 때 배포할 수 있는 상태로 유지한다. 운영 반영에는 사람의 승인 단계를 둘 수 있다. Continuous Deployment(지속적 배포)는 정한 검사를 통과한 변경을 별도의 수동 승인 없이 운영까지 자동으로 보낸다. 자동으로 운영에 반영해야만 DevOps를 하는 것은 아니다. [AWS 두 CD 비교](https://aws.amazon.com/devops/continuous-delivery/)

비교표는 같은 축인 **자동화가 어디까지 진행되고 운영 반영을 누가 결정하는가**로 그린다.

| 실천 | 자동으로 확인·진행하는 일 | 이 사례에서 남는 결정 |
| --- | --- | --- |
| CI | 변경 통합 후 빌드·테스트 | 배포 방법은 별도 |
| 지속적 전달 | 검사와 배포 준비, 테스트 환경 확인 | 운영 반영 승인 가능 |
| 지속적 배포 | 정해진 검사 후 운영 반영까지 | 승인 대신 미리 정한 정책·중단 조건 적용 |

GitHub Actions 같은 도구는 저장소의 이벤트에 따라 작업을 실행한다. 워크플로는 자동 작업의 정의이고, 작업(job)은 실행할 단계의 묶음이며, 실행기(runner)는 그것을 수행하는 컴퓨터다. 이 도구로 검사·빌드·배포를 연결할 수 있지만, 도구 설치만으로 협업과 운영 책임이 정해지지는 않는다. [GitHub 공식 구성 설명](https://docs.github.com/en/actions/get-started/understand-github-actions)

### 4. 무료배송 변경이 실제 사용자에게 도달하는 과정

아래는 구현을 약속하는 튜토리얼이 아니라 설명용 가상 절차다. 버전 이름도 가상이며, 경계 금액은 원고의 입력 조건이다.

| 단계 | 입력·행동 | 확인할 결과 | 문제가 있으면 |
| --- | --- | --- | --- |
| 변경 준비 | 3만 원 → 2만 원, 기존 장바구니 영향 논의 | 기대 동작·담당자·되돌릴 방법 합의 | 범위를 더 작게 나눔 |
| 통합·검사 | 커밋, 금액 경계와 주문 흐름 테스트 | 실패가 없는 검사 결과 | 배포 전에 수정 |
| 배포 준비 | `shop-v2` 생성, 테스트 환경 적용 | 버전·설정·검사 결과 연결 | 결과물을 다시 준비 |
| 운영 반영 | 같은 결과물을 제한된 트래픽에 적용 | 적용 버전과 대상 확인 | 확대 중단 |
| 관찰 | 버전별 주문 오류·응답시간 관찰 | 기존·신규 집단 차이 확인 | 영향 줄이기·복구 |
| 개선 | 빠뜨린 기존 장바구니 조건 조사 | 회귀 테스트와 다음 변경 | 책임 추궁 대신 재발 조건 제거 |

자동 검사에서는 새 장바구니만 시험했는데 운영에는 오래된 장바구니가 남아 있을 수 있다. 그 데이터에서만 오류가 나면 테스트 환경에서는 보지 못한 장애가 생긴다. 그래서 공개 후 사용자 상태를 관찰하는 과정이 필요하다. 이 가상 원인은 일반적인 환경 차이를 설명하기 위한 설정이며 실제 회사의 사고 원인으로 주장하지 않는다.

복구 수단에는 이전 버전으로 되돌리는 롤백, 기능 스위치 끄기, 수정 버전 반영이 있다. 어떤 수단이 가능한지는 변경의 성격에 달려 있다. 예를 들어 새 버전이 이미 데이터를 되돌릴 수 없게 바꿨다면 코드만 이전 버전으로 바꿔도 해결되지 않을 수 있다. 배포 전에 데이터 호환성과 복구 방법을 함께 정해야 한다. DORA의 데이터베이스 변경 관리 설명을 근거로 한 적용상의 설명이다. [DORA](https://dora.dev/capabilities/continuous-delivery/)

### 5. 전체 오류율 1%가 새 버전의 20% 오류를 가릴 수 있다

Google SRE 교재는 일부에 새 버전을 먼저 보내는 카나리 배포와 집단별 비교를 설명한다. 교재의 계산 예를 **같은 관찰 구간의 요청 1,000건**으로 다시 표현하자. 요청의 5%인 50건을 새 버전으로 보내고 그중 20%인 10건이 실패한다고 가정한다. 나머지 950건에서는 오류가 없다고 가정한다. 전체 오류율은 10 ÷ 1,000 = 1%지만 새 버전 오류율은 10 ÷ 50 = 20%다. 이것은 측정된 회사 성과가 아닌 **교재 설명의 비율을 적용한 계산 예**다. [Google SRE 원문](https://sre.google/workbook/canarying-releases/)

도해 2는 `기존 950건/오류 0건`, `신규 50건/오류 10건`으로 요청의 분모를 보여준다. 비교 막대는 같은 0–100% 축에서 전체 1%, 기존 0%, 신규 20%를 나타내고, 짧은 막대 옆에도 실제 수치를 써 둔다. 핵심은 “전체 값만 보면 새 버전의 문제를 과소평가할 수 있으므로, 같은 시간 구간에서 기존 버전과 신규 버전을 나누어 본다”이다. 1%나 20%를 모든 서비스의 중단 기준으로 제시하지 않는다.

### 6. 운영 상태와 전달 과정은 다른 질문을 측정한다

운영 화면에서는 요청의 지연, 트래픽, 오류, 자원 포화 정도를 살펴본다. 지연은 사용자가 응답을 기다리는 시간이고, 트래픽은 요청량이다. 오류는 실패한 요청이며, 포화는 자원이 한계에 얼마나 가까운지다. CPU가 낮아도 잘못된 응답이 많으면 사용자는 문제를 겪는다. 로그는 사건의 기록을 따라 원인을 좁히는 데 쓴다. [Google SRE 모니터링](https://sre.google/sre-book/monitoring-distributed-systems/)

DORA 지표는 지금 서버가 정상인지보다 **변경을 전달하는 과정이 어떻게 나아지고 있는지**를 묻는다. 2026-01-05 개정된 공식 지침은 다섯 지표를 제시한다. 한 애플리케이션·서비스의 맥락에서 함께 보고, 개인이나 서로 다른 서비스의 순위를 매기는 점수로 쓰지 않는다. [DORA 공식 지침](https://dora.dev/guides/dora-metrics/)

| 지표 | 답하려는 질문 | 필요한 기록 |
| --- | --- | --- |
| 변경 리드 타임 | 커밋부터 운영 반영까지 얼마나 걸렸나? | 커밋과 운영 배포 시각 |
| 배포 빈도 | 일정 기간에 운영 배포를 얼마나 했나? | 서비스별 배포 이력 |
| 실패 배포 복구 시간 | 즉시 개입이 필요한 배포 실패에서 얼마나 빨리 복구했나? | 실패 배포와 복구 시각 |
| 변경 실패율 | 배포 중 즉시 개입이 필요했던 비율은? | 실패 판정과 전체 배포 수 |
| 배포 재작업률 | 운영 사고 때문에 예정에 없던 배포를 한 비율은? | 사고 대응 배포와 전체 배포 수 |

### 7. 무엇을 먼저 공부할까?

다음 순서는 이 글의 독자에게 제안하는 학습 경로다. 제품을 모두 설치하는 목록이 아니라, 단계마다 설명하거나 만들어 볼 결과물을 둔다.

| 순서 | 배울 내용 | 확인할 결과물 |
| --- | --- | --- |
| 1 | Git 저장소·커밋·변경 검토 | 어떤 변경이 어느 버전에 들어갔는지 설명 |
| 2 | 테스트·실행 환경·빌드 결과물 | 경계값 검사와 실패 이유를 직접 확인 |
| 3 | CI 작업의 이벤트·단계·실행기 | 저장소 변경 후 자동 검사 결과를 읽음 |
| 4 | 테스트/운영 환경·설정·배포 권한 | 적용 버전과 승인자를 적은 배포 절차 |
| 5 | 오류·지연·로그·복구 | 실패 위치와 되돌릴 방법을 연결한 대응 메모 |
| 6 | 반복되는 환경의 코드 관리(IaC) | 환경 설정의 변경 이력을 검토하는 방법 설명 |

IaC(Infrastructure as Code)는 서버·네트워크 같은 자원의 구성을 코드로 관리하는 실천이다. 코드 검토와 변경 이력을 환경에도 적용한다. 컨테이너·Kubernetes·Terraform 등은 실제 환경의 필요에 따라 이어서 배울 도구다. 이 글은 그것들을 DevOps의 필수 시작 조건으로 삼지 않는다. 이는 도구보다 전달 과정의 문제를 먼저 찾는 DORA 지침을 적용한 편집 판단이다. [AWS IaC](https://aws.amazon.com/devops/what-is-devops/), [DORA 도입상의 함정](https://dora.dev/capabilities/continuous-delivery/)

### 8. 팀원들과 이야기할 한 장

팀의 최근 변경 한 건을 고르고 종이에 `커밋 → 검사 → 대기 → 배포 → 관찰 → 복구`를 그려 보자. 각 단계의 담당자·남는 증거·막히는 조건을 적는다. 가장 오래 기다리거나 같은 실수가 반복되는 단계 한 곳을 정하고, 다음 변경에서 바꿀 행동을 한 문장으로 합의한다. 이 활동은 DORA의 전달 과정 지도 만들기와 개선 논의를 이 글의 독자에게 맞게 줄인 것이다. 실제 학습 효과를 시험한 활동은 아니다. [DORA](https://dora.dev/capabilities/continuous-delivery/)

연습: “자동 검사와 테스트 환경 배포는 성공했지만 운영 반영은 팀장의 버튼 승인을 기다린다. 이 팀은 어떤 CD를 하고 있나? 그리고 전체 오류율 1%만으로 새 버전이 안전하다고 말할 수 있나?”

해설: 운영 반영에 수동 승인 단계를 둔 지속적 전달의 예다. 그 사실만으로 DevOps를 못 한다고 판단하지 않는다. 전체 오류율은 새 버전의 상태를 가릴 수 있으므로 버전별 오류의 분모·관찰 구간과 실제 사용자 영향을 함께 확인한다. 승인 방식은 자동화의 범위를, 집단별 오류는 공개된 변경의 결과를 설명한다.

공유용 요약은 본문을 검토한 다음 추출한다: **작은 변경을 함께 책임지고, 자동 검사로 빠르게 확인하며, 운영 결과를 다음 개선으로 연결한다.** 첫 화면에는 정의·변경에서 관찰까지의 대표 흐름·이 글을 읽고 만들 팀의 흐름도를 둔다. 장 수나 출처 수 배지는 첫 화면의 주 내용으로 쓰지 않는다.

### 내용과 첫 화면 자체 검토

제목·요약 점검 입력은 본문을 뺀 `first-screen.json`이다. 제목은 사용자가 지정한 “DevOps란?”을 유지하고, 부제에서 무료배송 조건 변경이라는 구체적 상황과 개발·운영의 연결을 밝힌다. 정의 다음에는 팀의 전달 흐름도와 개선할 한 지점이라는 독자 과제를 둔다. 이는 작성자가 선택 필드만 다시 읽은 점검이며 독립·맹검 검토가 아니다.

### 화면·인쇄 검증과 수정

별도 Edge/Playwright로 실제 파일을 오프라인에서 1440/768/390/320px로 열었다. 두 파일의 가로 넘침·중복 ID·누락된 본문 앵커·글꼴 로드·SVG 이름·런타임 오류·외부 요청을 검사했다. 목차와 모바일 접힘, 표의 키보드 가로 이동, 연습 해설, 발표 화살표/Space/Esc, 17장 화면 범위, 자세한 설명 패널, 발표/연속 읽기 전환, 10번째 장 직접 링크를 확인했다. 모바일 문서의 여섯 단계와 세 오류율 막대가 실제 표시되는 조건도 검사한다. 최종 영수증은 `page-checks.json`이다.

원본과 실제 캡처를 비교했다. Quarto의 삼단 읽기 구조·흰 배경·파란 탐색은 유지하고 한국어 본문 폭·줄간격·모바일 목차를 조정했다. 원본의 브랜드·검색창·책 소개 이미지는 제외했다. reveal 원본의 보라색 배경·큰 제목·진행 표시를 유지하고 가운데 브랜드 표지 대신 설명을 왼쪽에 배치했다. 4:3에 가까운 화면, 상세 설명, 모바일 연속 읽기는 추가한 동작이며 원본의 그대로 복제라고 주장하지 않는다.

검사 중 태블릿의 빈 우측 공간, 320px 인라인 코드 넘침, 기본 reveal 스크롤 모드의 과도한 축소, 읽기 모드 포인터 차단, 모바일 도표의 CSS 우선순위, 화면 번호/화살표 겹침을 수정했다. 모바일 도표는 작은 SVG 대신 같은 순서와 값의 HTML 목록/막대를 사용한다. 최초 앵커 검사에서 reveal의 유효한 `#/` 주소를 DOM ID로 오판한 검사도 수정했다. 실패 영수증은 성공과 구분해 보존한다.

브라우저 인쇄 출력은 문서6쪽·발표17쪽이다. 발표의 도표/출처 분리와 인쇄 색 대비를 수정했다. PDF 페이지를 PNG로 렌더링해 첫 장·흐름·카나리·학습 경로·연습을 직접 확인했다. 두 PDF는 인쇄 확인용 중간 산출물이다. 주거용 UI·제품 코드·발행 경로는 변경하지 않아 전체 주거 테스트나 brief/desk를 재생성하지 않았다.

검토 도구는 입력2MiB 제한으로 전체 글꼴이 포함된 약3MB HTML을 거절했다. 실제 공유 파일은 유지하고, 글꼴 데이터를 제외한 시스템 글꼴 미리보기 입력과 별도 `devops-study-review.html`/`devops-slides-review.html`을 생성했다. 글꼴·동작 차이를 화면에 알리고 실제 결과와 검토본의 해시를 `review-derivatives.json`에 보존했다. 이 정적 검토본을 상호작용 검증이나 최종 공유 파일로 취급하지 않는다. 이 시점의 기본 형식 선택은 미확정이었으며, 후속 선택은 아래 2판에 기록한다. 학습 효과·사람의 읽기 수용은 시험하지 않았다.

## 후속 선택과 학습 문서 2판

사용자는 앞에 요약정보와 간단한 목차를 두고, 슬라이드처럼 시각적인 자료를 보여주되 최종 형태는 공부 문서형 HTML로 정했다. 이에 기존 두 시범을 보존하고 `reports/devops-2026-10-10/devops-study-v2.html`을 새 판으로 만들었다. 공개 사이트나 공통 생성기로 자동 이행하지 않는다.

첫 화면의 순서는 제목·학습 상황, 핵심 요약, 네 가지 질문형 목차, 읽은 뒤 만들 팀의 결과물이다. 본문은 필요한 이유/변경 전달/관찰과 개선/공부와 팀 적용 네 묶음으로 나누고, 기존 8장의 주요 문단과 표를 모두 유지한다. 필수 내용은 일반 세로 스크롤에서 보인다. 접힘은 연습 해설과 라이선스에만 사용한다.

변경→관찰→다음 개선 흐름과 카나리 오류율을 큰 도해로 보여주고, 커밋·빌드 결과물·배포·공개, 경계값 검사, 두 CD의 승인 방식, 운영의 네 신호를 시각적으로 정리했다. 도해 아래에는 의미와 적용 조건을 설명한다. 1%/0%/20%는 원고와 같은 가상 계산이고 실측이나 보편적인 배포 중단 기준으로 바꾸지 않았다. 현행 DORA 다섯 지표와 공부 단계별 결과물도 유지한다.

### 2판 자체 검토와 출력 확인

제목·요약·목차를 본문과 별도로 읽어 독자가 DevOps의 공동 책임, 학습할 네 질문, 팀 흐름도라는 결과물을 파악할 수 있는지 자체 점검했다. 이후 전체 설명에서 한 쇼핑 사례의 입력·기대 동작·배포·관찰·복구가 연결되는지 대조했다. 이는 같은 작성자의 편집 검토이며 독립 검토나 사람의 이해도 시험은 아니다. 공식 원문은 같은 날 확보·검토한 위 8개를 재사용하며 HTML 재생성으로 수집일을 갱신하지 않았다.

별도 Edge/Playwright로 1440/1024/768/390/320px에서 실제 오프라인 HTML을 검사했다. 요약→목차→본문의 순서, 네 목차 이동, 데스크톱 탐색 키보드, 작은 화면의 여섯 단계/세 오류율 막대, 표의 키보드 가로 이동, 연습 해설, 인쇄 버튼과 인쇄 CSS, JavaScript 없는 기본 읽기를 확인했다. 중복 ID·끊긴 앵커·가로 넘침·런타임 오류·외부 요청은 없다. 모든 기존 주요 문단/표와 이전 두 파일의 SHA-256을 대조했다. `learning-v2-checks.json`과 `learning-v2-manifest.json`이 최종 결과를 기록한다.

첫 시각 검사에서 재사용한 Quarto CSS의 aside 열 지정이 새 두 열 구조에 간섭한 것을 발견해 새 레이아웃의 열을 명시하고 수정했다. 모바일의 어두운 도해에 본문 글자색이 상속되던 문제도 수정했다. 검사에 본문 폭·상단 위치·탐색 열 순서와 모바일 도해 레이블 색 조건을 추가했다. PC/모바일 첫 화면과 흐름·CI/CD·카나리·학습 경로 캡처를 직접 확인했다. 기존 검사 스크립트의 중복 클래스 strict-mode 오류는 제품 결함과 구분해 수정했고 실패 기록도 보존한다. 인쇄는 이번 판의 제어와 스타일을 확인했으며 새 PDF 생성·전체 쪽별 검토는 하지 않았다.

별도 `devops-study-v2-review.html`은 글꼴 데이터를 뺀 시스템 글꼴·스크립트 비활성 검토본이다. 실제 공유 파일은 전체 글꼴이 든 `devops-study-v2.html`이다. 차이와 해시는 `learning-v2-review-derivative.json`에 기록한다. 제품 소스·SQLite·주거 UI는 변경하지 않아 전체 주거 테스트나 brief/desk 재생성은 이번 범위에서 수행하지 않았다.

### 회사 공유 문체 보정

후속 정의 수정: 사용자가 “문화와 실천”이라는 정의를 거부해 현재 요약과 본문 정의를 코드 검사·배포·장애 대응의 담당자와 작업으로 설명했다. 자동화 도구 설명에도 검사 실패 수정자·배포 승인자·장애 담당자를 명시했다. 동일 사례·표의 값·출처는 유지하며 기존 AWS 스냅샷의 정의/작동/협업 절을 재대조했다. 신규 원문 수집은 없다. 수정 전 회사 문구판은 `devops-study-v2-before-concrete-copy.html`과 `learning-v2-before-concrete-copy-manifest.json`으로 보존한다. 작성 지침에는 추상 범주만으로 정의하지 않고 행위자·행동·조건·결과를 설명하도록 기록했다. 자체 이해 검토와 기술 검사는 사람 독자의 이해 확인을 뜻하지 않는다.

후속 사용자 요청에 따라 표제를 `요약`, `목차`로 바꾸고 `적용 과제`, `검토 질문`, `해설`로 안내 표현을 정리했다. 목차·장 제목은 주제명 중심으로, 도입과 학습/팀 점검 문단은 업무 문서의 설명·절차 문장으로 수정했다. 레이아웃, 도표의 값과 분모, 공식 출처와 수집일은 유지한다. 수정 전 2판과 manifest는 `devops-study-v2-before-company-copy.html` 및 `learning-v2-before-company-copy-manifest.json`으로 보존했다. 현재 결과의 명시적 본문 변경 목록은 `learning-v2-manifest.json`의 `copy_edits`에 기록한다. 수정 문구·주변 본문·표 데이터를 대조하고 PC/모바일 실제 표시를 확인했다. 새 조사·사람 이해도 시험은 아니다.

### 상단 목차와 이전 페이지 복귀

사용자가 기존 리서치 좌측 탐색과 문서 목차의 중복을 지적하고, 목차로 이동한 뒤 이전 페이지로 돌아갈 수 있는 동작을 요청했다. 현재 로컬 2판의 문서 목차를 본문 위로 옮겼다. PC에서는 네 장의 상단 목차, 850px 이하에서는 `목차` 접힘 메뉴를 제공하고 현재 읽는 장을 표시한다. 본문 첫 부분의 `요약`·`목차`는 유지한다.

상단 `뒤로`는 브라우저 방문 기록을 따라 이전 장의 읽기 위치 또는 이전 페이지로 돌아간다. 목차의 일반 앵커 이동은 기록을 만들며, 일반 스크롤과 현재 장 표시는 기록을 추가하거나 주소를 변경하지 않는다. 이전 기록 없이 직접 열면 `리서치 목록` 링크를 표시한다. 링크 목적지는 `https://hansihoo.github.io/signal-desk/preview/index.html`이다. 실제 이전 페이지에서 문서를 열고 목차를 이동한 뒤 두 번 돌아가 원래 페이지가 표시되는 흐름을 PC/모바일에서 확인했다. 온라인 목록 페이지의 렌더링은 이번 검증 범위 밖이다.

목차 이동 직전의 스크롤 위치를 현재 기록에 저장하고 뒤로갈 때 복원한다. 검증 중 루트 `scroll-padding-top` 때문에 상단 링크의 포커스가 본문을 먼저 위로 이동시키는 문제가 발견됐다. 루트 대신 본문 대상의 `scroll-margin-top`에 여백을 적용해 수정했다. 모션 설정에 따른 부드러운 이동은 활성 장·제목 위치 조건이 충족될 때까지 기다려 검사한다.

수정 전 파일과 manifest는 `devops-study-v2-before-top-nav.html` 및 `learning-v2-before-top-nav-manifest.json`으로 보존했다. 이전 파일과 현재 파일의 `main` 전체 텍스트가 정확히 같고 도해·표·출처를 유지한다. 새 제어 코드는 `devops-navigation.js`에서 최종 단일 HTML에 내장한다. `learning-v2-manifest.json`은 navigation revision1과 실제 결과의 해시를 기록한다.

앱 브라우저 연결 실패로 별도 Edge에서 오프라인 검증했다. 1440/1024/850/768/390/320px의 목차·이전 위치 복원·앞/뒤 이동·키보드, 모바일 메뉴 선택/Escape/바깥 클릭, 스크롤 중 활성 장 표시와 방문 기록 불변, 직접 장 링크, 실제 이전 페이지 복귀가 `navigation-v2-checks.json`의 10기록을 통과했다. 기존 본문·원본 해시·앵커·도표·인쇄 스타일·JavaScript 없는 읽기와 정적 검토본을 검사하는 `learning-v2-checks.json`의 9기록도 최종 결과에 맞춰 다시 통과했다. 가로 넘침·런타임 오류·외부 요청은 없었으며 PC/모바일 첫 화면과 열린 모바일 메뉴 캡처를 직접 확인했다. 초기 실패 기록은 최종 성공과 구분해 보존한다.

정적 검토본은 최종 파일로부터 다시 생성했으며 시스템 글꼴·스크립트 비활성 조건은 동일하다. 이번 변경은 로컬 시범 탐색만 대상으로 한다. 공개 페이지·공통 생성기·SQLite·원문 수집일을 변경하지 않았으며 새 조사·사람의 이해도 시험·공개 배포는 수행하지 않았다.
