# 질문과 근거를 연결하는 보고서 생산

2026-10-09 사용자 피드백을 반영한 실행 계약이다. 글의 목적은 독자가 새로운
지식을 얻고 판단하거나 행동하는 것이다. 제목·표·출처 개수만으로 합격시키지 않는다.

## 기존 구조에서 발견한 원인

기존 수집기는 RSS/Atom·공개 페이지를 SQLite에 저장하지만, 학습·시장 보고서를
자동 집필하지 않았다. 에이전트가 작성한 JSON을 `research-data` 또는 불변 발행
배치로 가져왔다. `validate_report`는 형식·수치·출처 ID를 검사했고 `review`는
주거 자료와 출력 상태를 검사했다. 이 결과를 내용의 유용성이나 근거의 충분성으로
확대하면 안 된다. 작성 지침은 있었지만 실행되는 질문별 근거 검사와 재작업 경로가 없었다.

## 실행 흐름

`research-run`은 다음 단계를 연결한다.

1. 독자·핵심 질문·읽은 뒤 할 일에서 질문을 세분화하고 조사 방법을 선택한다.
   `research_type=auto`는 모델이 유형을 선택한다. 미리 검토한 `questions`를 주거나
   `plan_questions=false`로 지정하면 추가 계획 호출을 생략한다.
2. 질문에 필요한 근거를 선언한다. 기술 학습, 시장, 사업 기회, 도구 비교,
   최신 변화의 기본 조사 방법이 다르다. 기타/좁은 범위는 `custom_profile`의
   `method`와 `requires`로 이유와 근거를 명시한다. 목차는 강제하지 않는다.
3. 후보 URL의 원문을 수집한다. 검색 결과나 피드 제목을 원문 증거로 쓰지 않는다.
   공개 원문을 읽을 수 없으면 실패로 남긴다. PDF/첨부는 현재 별도 추출이 필요하다.
4. 원문 인용·의미·조건·한계와 질문별 답·논거를 연결한다. 수치에는 모집단·기간·단위·
   비교 기준을 남긴다. 발주 예산, 판매 호가, 실제 지급액을 구분한다.
5. 분석을 바탕으로 본문과 예제를 쓰고 제목·소개·요약을 확정한다. 기존 보고서v1을
   그대로 출력하며 별도의 claims/answer_paths가 근거와 설명 위치를 연결한다.
6. 제목·소개만 제공하는 검토와 원문·분석·본문을 제공하는 검토를 별도 호출한다.
   각 판정은 이유와 실제 위치를 포함한다. 본문을 본 결과로 첫 화면 이해를 대신하지 않는다.
7. 근거 부족은 research, 오독·비교 오류는 analysis, 설명·표현 문제는 writing으로
   돌아간다. 설정한 횟수 안에 해결되지 않으면 `blocked`로 종료하며 발행하지 않는다.

추가 원문 탐색은 `--discover`로 명시적으로 켤 수 있다. 요청의 `allowed_domains`에
제한한 OpenAI 웹 검색을 최대1회 사용하며 API 응답의 실제 조회 URL에 포함된 후보만
채택한다. 이후 HTTP 원문 수집이 성공해야 근거로 사용할 수 있다. 검색에서 읽혔다고
직접 수집 실패가 성공으로 바뀌지는 않는다. 검색을 끄면 후보가 없을 때 구체적인 조사
부족을 남기고 중단한다. 발주 사이트의403/목록 이동 같은 접근 제한을 우회하지 않는다.

## 데이터와 발행 호환성

보고서v1, 기존 ID·HTML 디자인·보고서 판 보관 방식은 유지한다. 새 메타데이터를
보고서 본문 스키마에 넣지 않는다. 별도의 quality package에 계획, 원문 수집 상태,
선택 발췌, 분석, 주장 위치, 두 검토의 입력 지문과 결과를 둔다.

SQLite에는 `research_originals`(원문/수집 날짜), `research_generation_cache`
(입력·모델·프롬프트·원문 지문별 결과), `research_workflow_runs`(성공/중단·비용 사용량),
`research_quality_batches`(발행한 품질 패키지)가 추가된다. 원본 바이트는 `data/raw/`에 둔다.
첫 수집일, 마지막 성공 수집일, 원문 게시일, 실제 검토 기록을 구분한다. 캐시 재사용이나
HTML 재생성은 자료 확인일을 갱신하지 않는다. 실패한 재수집은 옛 텍스트를 새 근거로 제공하지 않는다.
새 원고의 `checked_on`은 모델 출력 대신 실행기가 집필 시점의 UTC 날짜로 정한다.
캐시에서 같은 원고를 읽을 때는 기존 날짜를 유지한다. 수집 영수증의 성공 시각과
첫 화면/본문의 실제 검토 시각은 각각 별도로 보관한다. 이 날짜 정책을 적용하기
이전의 단계 캐시는 새 생성 캐시 버전에서 재사용하지 않는다.

발행 manifest의 배치에 `quality` 파일명을 연결하면 보고서 내용 지문·출처 URL·원문
발췌·질문별 근거·주장 연결·검토 입력 지문을 발행 전에 검사한다. 보고서나 품질
패키지를 바꾸려면 새 불변 배치를 추가한다. 검사를 실패하면 보고서/발행 영수증의
트랜잭션을 반영하지 않는다. 생성 결과는 기본적으로 발행하지 않으며 ready 산출물만
보고서v1 JSON과 quality JSON으로 함께 내보낸다. `--import-reviewed`는 검사 후 SQLite
보고서 판에 반영하고, 배포는 기존 명령/워크플로를 사용한다.

이전 배치는 계속 읽는다. 기존 문서를 새 기준의 합격작으로 간주하지 않는다.
`research-audit`는 설정된 최신 판의 상태를 `gated_agent_review` 또는
`needs_substantive_review`로 보고한다. SQLite에 별도로 편집된 판의 감사는 이 명령의
범위가 아니다. `research-data --input`은 이제 `--quality`가 필요하다. 예전 호출을
계속해야 한다면 `--legacy-unreviewed`를 명시해 경고와 함께 가져올 수 있지만 내용
검토로 기록되지 않는다. 하위 `import_reports` API도 기존 호환을 위해 유지한다.

## 사용

요청 예시는 [research_request.example.json](../config/research_request.example.json)이다.
같은 프로젝트의 기존 등록된 임시 출력 위치를 사용한다. 새 작업 폴더를 만들지 않는다.

```powershell
python -m housing_watch research-plan --input config/research_request.example.json --output reports/research-teaching-2026-10-09/pipeline-plan.json
python -m housing_watch research-audit --output reports/research-teaching-2026-10-09/pipeline-quality-coverage.json
python -m housing_watch research-check --input config/research_quality_pilot.2026-10-09.json --quality config/research_quality_pilot.2026-10-09.quality.json
```

유료 API 실행에는 계정의 `OPENAI_API_KEY`와 직접 선택한 모델 ID가 필요하다.
키와 모델을 저장소에 쓰지 않는다. `--model <선택한 모델 ID>`를 지정한
`research-run --input ... --output ... --raw-root ...`로 실행한다. 선택적으로
`--reviewer-model`, `--discover`, `--import-reviewed`를 사용한다. 서버가 incomplete/refusal/
잘못된 JSON/전송 오류를 반환하면 자동으로 재과금 재시도하지 않고 중단 기록을 남긴다.

OpenAI 연결은 [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create),
[구조화 출력과 JSON 모드](https://developers.openai.com/api/docs/guides/structured-outputs),
[웹 검색의 도메인 제한·sources](https://developers.openai.com/api/docs/guides/tools-web-search)를
확인해 구현했다. JSON 모드 뒤에도 프로그램이 실제 스키마를 검증한다. `store=false`,
모델별 명시 설정, API 키 비노출, 별도 문맥의 검토를 사용한다.

## 비용과 검증 한계

- 계획·검사·감사·기존 발행은 모델 호출0회다. 일일 Pages 배포는 유료 생성을 켜지 않는다.
- 새 요청은 보통 계획1 + 분석1 + 집필1 + 첫 화면 검토1 + 본문 검토1의5회다.
  질문이 준비됐으면4회다. 변경 없는 재실행은 원문 캐시와 단계별 생성 캐시를 재사용한다.
- 기본 상한은 모델10회, 원문6회, 보완 검색1회, 생성2회차다. 호출별 출력10,000토큰,
  입력120,000문자 상한을 적용한다. 입력이 크면 근거를 몰래 잘라내지 않고 중단한다.
  HTTP/모델 오류도 시도 횟수에 포함한다. 입력/출력 토큰과 웹 도구 호출 수를 기록한다.
- 금액 상한은 아니다. 실제 달러 비용은 선택한 모델의 입력·출력 단가, 검색 단가와
  실제 사용량으로 계산한다. 거절/불완전 응답에 제공되지 않은 토큰 사용량은 확인 불가다.
- 기계 검사는 인용 문자열과 지문·연결의 일치를 증명한다. 그 구절이 주장을 충분히
  뒷받침하는지, 글로 실제 학습하는지는 별개다. 의미 검토도 모델의 오류를 완전히 제거하지
  못한다. 기본 검토는 같은 모델의 새 문맥이며 필요하면 reviewer 모델을 따로 지정한다.
- 이번 시장/RAG 시범은 실제 원문을 읽은 에이전트가 작성하고 서로 다른 에이전트가
  첫 화면/본문을 재검토했다. 유료 생성 API의 실계정 실행, 실제 독자 시험, RAG API 실습은
  하지 않았다. 모델 연결은 요청/응답 fixture와 전체 오케스트레이션 회귀 시험으로 검증했다.
  실서비스 모델별 JSON 모드·웹 검색 지원, 출력 길이·비용·실패율은 실계정 운영 평가가 남는다.
- 시범 패키지의 원문은 웹 도구로 읽은 관련 절과 보존한 수집 영수증에 바탕을 둔다.
  config에는 짧은 선택 발췌와 지문만 보관한다. 전체 원문 보관 파일은 Git에 포함하지 않으므로
  CI의 문자열 검사는 보관 원문 자체를 재다운로드하거나 사실을 독립 검증하는 시험이 아니다.
