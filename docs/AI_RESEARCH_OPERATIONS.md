# AI 개발자와 관리자를 위한 조사 운영

문서화일: 2026-10-09. 사용자가 합의한 조사 방향을 다음 에이전트가 이어받기 위한 운영 기준이다.
AI로 개발 업무, 제품, 조직, 인력시장이 어떻게 바뀌는지 조사해 독자의 학습과 판단을 돕는다.
사용자가 용어를 알려줄 때만 찾지 말고, 중요한 변화와 아직 다루지 않은 주제를 찾아 제안한다.

이 문서의 절차는 에이전트의 조사 작업에 적용한다. 새 수집기, 날짜 데이터 계약,
전 분야 예약 실행이 구현되었다는 뜻은 아니다. 구현 상태는 [프로젝트 상태](../PROJECT_STATUS.md)에 기록한다.

## 독자와 조사 목적

개발자는 무엇을 배우고, 어떤 도구를 선택하고, 어떻게 구현·운영하며, 어떤 역량을 준비할지 판단할 수 있어야 한다.
관리자는 어느 업무에 AI를 도입하고, 비용과 효과를 어떻게 평가하며, 필요한 인력·책임·조직을 어떻게 구성할지 판단할 수 있어야 한다.
같은 자료라도 독자의 질문에 따라 설명과 필요한 근거가 달라진다. 모든 글을 SDK 구현 실습으로 만들지 않는다.

한국과 해외 사례를 함께 찾되 지역, 산업, 조직 규모, 경력 수준, 관찰 기간을 보존한다.
해외의 특정 기업 사례나 플랫폼 이용자 표본을 한국의 전체 시장으로 일반화하지 않는다.

## 조사 범위

아래 범위는 누락을 찾기 위한 지도다. 키워드가 없는 새 역할이나 문제를 배제하는 필터로 쓰지 않는다.

| 영역 | 조사할 질문과 내용 |
| --- | --- |
| 모델·개발 도구 | 새 모델과 코딩 도구로 어떤 작업이 가능해졌나? 기능, 지원 환경, 비용, 실제 평가 조건, 전환·종료 일정 |
| 지식·데이터 | AI가 업무 정보를 정확히 쓰려면 무엇이 필요한가? 지식베이스, RAG, 온톨로지, 지식 그래프, 데이터 품질·갱신·접근권한 |
| 실행·운영 | AI를 실제 업무에 연결하고 실패를 관리하려면? MCP·도구 호출, 문맥·메모리, 워크플로, 평가, 관측, 사람 승인, 복구 |
| 기업 도입·조직 | 시연이 운영 성과로 이어지려면? FDE, 도메인 전문가, 기존 시스템 연동, 업무 변경, 역할·책임·조직 구성 |
| 제품·사업 | 누가 어떤 문제에 비용을 지불하나? 고객 요구, 적용 사례, 경쟁·가격, 도입 비용과 효과, 외주·지원사업 |
| 인력시장·역량 | 채용과 업무 구성이 어떻게 바뀌나? 신입·경력, 직무·지역별 수요, 임금, 새로운 역할, 필요한 학습·경력 경로 |
| 보안·책임 | 도입 조건과 실패 위험은? 프롬프트 주입, 개인정보, 권한, 라이선스, 보안 사고, 정책·규정과 적용 대상 |
| 산업별 적용 | 문서·개발·고객지원·제조 등에서 실제로 무엇이 바뀌나? 업무 단계, 사람과 AI의 분담, 성과 측정, 한국 적용 조건 |

온톨로지·지식베이스·FDE·인력시장 변화는 명시적인 조사 대상이다.
피지컬 AI처럼 새로운 적용 분야도 독자의 개발·관리 판단에 영향을 주면 범위에 추가한다.
‘모든 주요 정보를 수집했다’고 선언하지 말고, 다룬 질문과 남은 공백을 표시한다.

문서 날짜가 더 최근이라는 이유만으로 기존 사용자 승인이나 분야별 주기를 바꾸지 않는다.

## 초기 지식 정리

처음에는 현재 보고서를 위의 질문에 대응시켜 무엇을 설명하고 무엇이 빠졌는지 확인한다.
2026-10-08의 작성 보고서 20편 보강은 기존 원고의 개선이며, 위의 전 범위를 채운 작업은 아니다.
온톨로지, 지식베이스 운영, FDE와 도입 조직, AI와 인력시장처럼 부족한 영역을 우선 검토한다.

기초 지식은 최근 7일로 제한하지 않는다. 오래된 자료라도 현재 문제를 설명하는 데 필요하면
최신 규격·적용 조건을 확인해 연결한다. 개념 설명, 최근 변화, 실제 적용 사례, 독자의 첫 행동을 함께 구성한다.
설명과 일관된 사례를 먼저 쓰고 제목·요약·표를 만든다. 글쓰기 절차는 연결된 작성 기준을 따른다.

## 알려주지 않은 주제도 발견하는 절차

1. 개발자·관리자의 질문과 이전 검토의 공백을 확인한다. 새 기능뿐 아니라 비용, 실패, 조직, 채용 변화도 탐색한다.
2. 출처 목록의 새 자료와 기존 자료의 수정 내용을 살피고, 공식 기술 문서·도입 사례·채용 공고·시장 연구를 교차 탐색한다.
3. 반복 등장하는 낯선 용어·역할·문제를 발견하면 정의, 필요한 이유, 대안, 요구 역량을 원문으로 확인한다.
4. 반대 사례와 제한을 찾는다. 같은 보도자료의 재인용은 독립 근거로 세지 않는다. 조회 수와 화제성은 사실 검증을 대신하지 않는다.
5. 기존 보고서와 비교해 신규 주제, 의미 있는 변경, 근거 보강, 중복으로 구분한다.
6. 독자가 학습·도입·채용·사업 판단을 바꿀 수 있는 내용을 선정한다. 보류한 후보도 이유와 다음 확인을 기록한다.

예를 들어 FDE를 발견했다면 직함의 정의에서 멈추지 않는다. 고객 현장에서 맡는 업무,
개발·영업·컨설팅과의 관계, 도입 장애, 요구 역량을 확인한다. 여러 회사의 공고와 도입 사례를
찾되 한 회사의 채용만으로 시장 수요 증가를 단정하지 않는다. 사용자가 ‘FDE’를 입력하지 않아도 이 절차를 수행한다.

연구 자료는 방법, 표본, 측정 기간, 실행 조건, 심사·개정 상태를 확인한다.
공급사의 성과 설명은 자체 주장으로 표시하고 독립 평가와 구분한다.
채용 공고는 개별 수요의 근거이며 전체 고용 변화의 측정값은 아니다.
AI에 노출되는 업무 비중을 실제 실업률이나 인원 감축 효과로 바꾸지 않는다.

## 출처 연결과 상태

[출처 목록](AI_RESEARCH_SOURCES.md)은 조사자가 참고하는 등록부다. 런타임 수집 설정과 다르다.
목록에 넣었다는 이유로 RSS·API·HTML 수집이나 예약이 연결됐다고 보고하지 않는다.
연결할 때는 실제 지원 경로를 확인하고 출처별로 하나씩 검증한다. 피드 주소를 추측하지 않는다.

출처별로 원문·목록 주소, 찾으려는 질문, 수집 방법, 목표 주기, 실제 연결 상태,
마지막 시도와 성공, 오류·누락 범위를 관리한다. 목록 수집 성공은 원문·첨부의 내용 검토 성공이 아니다.
차단·오류가 발생하면 기존 데이터와 마지막 성공 기록을 보존한다.
월간 점검에서 누락 분야, 특정 공급사 편중, 끊어진 경로, 새 출처 필요성을 확인한다.

## 날짜 기록의 의미

수집 날짜는 반드시 기록한다. 아래 항목을 같은 날짜로 대체하지 않는다.
공통 저장·내보내기 계약을 확장할 때 적용할 요구사항이며, 현재 보고서 v1의 새 필드가 아니다.

| 날짜 | 기록 기준 |
| --- | --- |
| 원문 발표일 | 원문이 제공한 값과 근거. 날짜만 있으면 날짜 정밀도를 유지하고, 없으면 미확인 |
| 원문 수정일 | 원문이 명시한 수정일. 에이전트가 변경을 발견한 시각과 구분 |
| 최초 수집 시각 | 실제 처음 자료를 확보한 시각. 재수집해도 변경하지 않음 |
| 최근 성공 수집 시각 | 해당 자료를 실제 다시 확보한 시각. 내용이 같아도 기록하며 실패 시 갱신하지 않음 |
| 변경 발견 시각 | 의미 있는 변경을 처음 관찰한 시각. 원문의 수정일로 추정하지 않음 |
| 내용 검토 시각 | 원문과 해당 주장·조건을 실제 확인한 시각과 범위. 생성·렌더링 시각으로 대체하지 않음 |
| 측정 기간·적용일 | 통계의 관찰 기간, 기능·정책 시행일, 종료일, 공고 마감. 발표·수집 날짜와 별도로 기록 |
| 다음 확인 예정 | 변화 속도와 영향에 따른 점검 기한. 기한 경과만으로 원문이 틀렸다고 단정하지 않음 |

시스템 이벤트는 시간대가 있는 UTC 시각으로 저장하고 독자에게는 한국시간으로 표시하는 방향을 따른다.
원문이 날짜만 제공하면 시각·시간대를 만들어 붙이지 않는다. 기존 자료의 최초 수집일을 모르면
오늘로 소급 입력하지 않는다. 이번에 확인한 시각과 최초 수집 미확인을 따로 남긴다.

가상 예: 9월 15일 발표된 글을 10월 8일 처음 수집하고 9일 다시 확보했다면 발표일은 9월 15일,
최초 수집은 8일, 최근 성공 수집은 9일이다. 10일 수집 실패는 최근 성공일을 바꾸지 않는다.
11일 HTML을 다시 만들어도 내용 검토일은 실제 원문 검토를 하지 않았다면 그대로다.

가격·이용 가능 여부·종료 일정·보안·신청 마감처럼 빨리 바뀌는 조건은 사용·재게시 전에 다시 확인한다.
점검 기한이 지났거나 중요 자료를 읽지 못했으면 확인 범위와 ‘재확인 필요’를 표시한다.

현재 뉴스 SQLite에는 `published_at`, `first_seen_at`, `last_seen_at`이 있다.
`last_seen_at`은 수집 경로에서 다시 관찰한 시각으로, 원문 전체 검토를 보증하지 않는다.
공개 source export는 `published_at`·`first_seen_at`을 제공하며 `last_seen_at`은 아직 내보내지 않는다.
raw snapshot의 `fetched_at`, 모델 관측 날짜, 보고서 `checked_on`, 판의 저장·수정 시각,
export 생성 시각도 서로 목적이 다르다. 공통 원문별 검토·재확인 상태는 후속 구현이다.

보고서 v1의 `checked_on`과 references의 `id`, `title`, `url`, `description` 계약은 유지한다.
검증되지 않은 날짜 필드를 기존 JSON에 추가하지 않는다. 공통 계약을 구현하기 전에는
[검토 기록](ai/AI_RESEARCH_REVIEW_LOG.md)에 원문 URL, 실제 확인 시각·범위, 날짜 근거와 남은 공백을 기록한다.

## 반복 검토와 변경이 있을 때만 게시하기

목표는 일일 후보 탐색과 주간 심층 검토다. 일일 실행은 후보 발견이며 모든 자료의 심층 검토 완료를 뜻하지 않는다.
이 문서화 작업에서는 예약을 생성·변경하지 않는다.

| 경로 | 현재 상태와 유지할 원칙 |
| --- | --- |
| 기존 클라우드 수집·배포 | 기존 설정 출처를 매일 한국시간 약 05:00에 갱신하는 워크플로 유지. 실제 실행 성공은 별도 확인 |
| 모델 전용 유지 | 모델 운영 문서의 매일 05:00 신규·변경 검토 범위 보존. 전 분야 주간 검토로 낮추지 않음 |
| 사업기획 전용 유지 | 사업기획 문서의 월요일 09:00 주간 검토와 비공개 데이터 경계 보존 |
| 전 분야 후보 탐색·심층 검토 | 이 문서로 절차 정의. 확대 출처 연결·반복 실행은 미구현; 공통 주간 요일·시각 미정 |

후속 예약 작업에서는 기존 예약을 먼저 확인해 중복을 피한다.
보안 사고, 서비스 종료, 중요한 마감 등 대응 시점이 빠른 변화는 발견 시 우선 검토한다.

매 검토에서는 다음 순서를 따른다.

1. 이전 성공 시각, 실패, 보류 후보와 실제 작업 시작 시각을 확인한다.
2. 신규 자료뿐 아니라 수정·정정·철회·종료를 확인한다. 최근 7일이나 피드 신규 목록만으로 판정하지 않는다. 실패 기간의 공백도 복구한다.
3. 출처·범위별 결과를 **신규 / 변경 / 변경 없음 / 수집 실패 / 검토 미실행**으로 기록한다. 일부만 읽었다면 읽은 범위와 빠진 범위를 나눈다.
4. 고정 출처 확인과 함께 알려지지 않은 주제·기존 지식 공백을 탐색한다.
5. 선정한 자료의 의미, 조건, 반대 근거와 계산을 확인하고 독자 질문에 맞춰 작성한다.
6. 실질적 내용 변경이면 같은 보고서 ID의 새 불변 배치·판으로 게시한다. 새 주제에는 새 ID를 쓴다. 확인일만 바뀌었다고 새 원고 판을 만들지 않는다.
7. 의미·근거 검토, 독자 이해 자체검토, 기술 출력 검증을 나눠 기록한다. 게시 권한과 검증은 기존 게시 운영을 따른다.

목록을 못 가져왔거나 원문·첨부를 못 읽었거나 수집 제한으로 일부만 확인했다면 ‘변경 없음’으로 처리하지 않는다.
정상적으로 확인한 범위에서만 변경 없음이라고 말한다. 의미 있는 변화, 실패, 판단이 필요한 항목을 알리고 반복적인 무변화 알림은 피한다.

## 지식베이스와 보고서 연결

원문·날짜·주장·개념·적용 사례·독자 역할·관련 보고서와 과거 판을 연결해 같은 질문을 다시 조사할 때 재사용한다.
예를 들어 지식베이스에서 데이터 갱신·권한 문제를 배우고, 온톨로지에서 업무 개체·관계를 이해하며,
FDE 도입 사례에서 그 지식이 기존 시스템과 조직에 연결되는 과정을 읽을 수 있게 한다.
이는 지식 연결 원칙이며 새 그래프 DB를 도입하라는 지시가 아니다.

메인에는 최근 중요한 변화와 독자에게 미치는 영향을, 보고서에는 개념·작동 이유·완결 사례·조건·첫 행동을 둔다.
필수 이해 내용은 본문에 보이고 선택 심화만 펼치기에 둔다. 원문 근거는 주장 가까이 연결한다.
수치·비교·시장 보고서는 측정 대상과 읽는 방법, 그 자료로 알 수 없는 범위까지 설명한다.
요약·표·분류 수가 늘었다는 이유로 유용한 보고서라고 판정하지 않는다.

공개 자료만 공개 수집·보고서·백업에 넣는다. 개인 프로필, 비공개 고객·가격·계약·사내 자료는
기존 비공개 경로를 따른다. 원문과 과거 보고서 판을 보존하고 상충하는 근거를 숨기지 않는다.

## 완료 기록과 후속 구현

완료 보고에는 조사 질문·확인 범위, 원문과 날짜, 새로 발견한 주제, 선정·보류 이유,
독자가 배워야 할 결과, 남은 공백을 기록한다. 확인 가능한 주장과 해석을 구분한다.
실제 독자 시험이나 실행 실습을 하지 않았다면 수행했다고 쓰지 않는다.
구조 검증·테스트 통과는 글의 이해 가능성을 입증하지 않는다.

후속 구현은 날짜·출처 상태 계약, 출처별 연결, 새 주제 발견·중복 판단, 전 분야 반복 검토 순으로 나눈다.
저장·export·렌더러 호환성과 실패 시 보존을 검증한 기능만 완료로 표시한다.
수동으로 가능한 에이전트 절차와 아직 연결되지 않은 자동 실행을 [프로젝트 상태](../PROJECT_STATUS.md)에서 구분한다.
