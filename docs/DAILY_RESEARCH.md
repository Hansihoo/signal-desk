2026-10-21 사용자 요청에 따라 확인할 질문·최신 목록·접근 방식·수집 공백을 미리 조사했다.
큰 사건을 포함한 오전 일일 브리핑이 쓰는 준비 절차다. 알림 선정/전달은

회사 증빙은 공개 목록 캐시/전달 기록에 섞지 않는다.

## 매일 실행 순서

1. 직전 실제 성공/원문 검토/전달 시점과 중요 재확인을 확인한다. 날짜만 바꾼 재보고를 피한다.
2. 기존 AI 공개 후보를 동기화하고 아래 준비 명령으로 사업/유사 기업 목록을 한 번에 모은다.
   최대4개 병렬 HTTP와 조건부 GET,30분 성공 캐시를 사용한다. 캐시 재사용은 새 획득/독해로 기록하지 않는다.
3. 기술과 사업 후보를 함께 살핀다. 저장은 전량 보존하고 표시 limit만 제한한다. 준비 대기열은
   실제 변경 관찰 시각으로 정렬하고 출처별로 번갈아 배치해 긴 기업 목록이 다른 공고를 밀어내지 않게 한다. `new`는 새로 관찰한
   목록 URL이며 신규 출시 확정이 아니다. 최초 성공 목록은 `baseline`이고 새 소식 알림으로 일괄 전환하지 않는다.
   같은 queue 결과의 deadline_hints도 매일 확인한다. 이는 기존/미변경/baseline 공고를 포함해
   KST 기준 오늘부터7일 안의 목록상 마감 날짜를 뽑는다. 원문 모집 상태·정확한 시각·연장/정정은
   미확인이므로 별도 재확인한다. 예산 소진 등 날짜 미상은 unresolved_period_count로 남긴다.
4. 자동 수집7경로의 범위 밖인4개 브라우저 경로와 국책 검색 묶음을 실제 확인한다.
   NIPA/기업마당 첫 목록만으로 관심 분야를 다 확인했다고 하지 않는다. `plan`의 검색어 묶음은
   각 단어를 개별 검색하거나 사이트가 지원하는 OR로 사용한다. 여러 단어를 AND로 붙여 누락시키지 않는다.
   최근7일을 출발점으로 직전 성공 이후 공백까지 넓히고, 필요한 이전 페이지를 읽는다.
   피드 제공 창보다 긴 공백·페이지 상한·열람 실패가 있으면 확인 범위를 남기고 공고 없음으로 바꾸지 않는다.
5. 중요한 후보만 공식 상세/첨부·조건·이전 발표와 대조한다. 국책사업은 회사 프로필 기준으로
   판정·참여 역할·적합 이유·추가 확인 조건·KST 마감·공식 출처/확인일을 준비한다.
   기업은 방향/실제 제공/제품 연결을 확인한다. 공식 가격과 발표 날짜도 필요할 때 현재 원문으로 재확인한다.
6. 일일09:00에는 주요 이슈와 큰 사건/대응 시점이 빠른 기회를 한 번에 묶는다. 큰 사건은 눈에 띄게 구분한다.
   기존 모델/일일/과거 별도 알림/주간 메시지를 대조하고 실제 알릴 항목의 원문·중복/수신만 최소 기록한다.
   모든 후보를 기사로 만들거나 탈락 사유를 개별 작성하지 않는다.

오전 일일 확인은 준비 결과의 새/변경 후보와 중요한 보류·임박 공고부터 본다. 준비 캐시/이전 검토를
재사용하고 필요한 공식 경로를 추가 확인한다. 일반 목록을 반복 전송하지 않고, 실제 미확인을
검토 완료로 처리하지 않는다. 일일에도 회사 기준 선별을 하고, 증빙 보강·제품 적합성
심화·사업 화면 갱신은 기존 주간 작업이 맡는다.
새 모델 소개/전체표의 동시 반영은 매일05:00 모델 예약이 맡으며 중복 발행하지 않는다.

## 바로 쓰는 명령

```powershell
# plan과 queue는 원본/캐시를 쓰지 않는 읽기 명령
python -m housing_watch.daily_research plan
git signal-gh verify
python -m housing_watch.signal_review sync-public
git signal-gh verify
python -m housing_watch.signal_review queue --limit 12
# collect도 자체적으로 정확한 루트/원격/Hansihoo guard를 먼저 실행
python -m housing_watch.daily_research collect
python -m housing_watch.daily_research queue --limit 24
# 최초 연결 당시의 자료를 배경으로 살필 때만 포함; 신규 출시로 간주하지 않음
python -m housing_watch.daily_research queue --include-baseline --limit 24
```

`collect --force`는 최근 캐시도 HTTP로 재확인한다. 목록 획득/파싱 실패는 종료코드1과
failed/마지막 성공으로 표시한다. browser_required는 브라우저에서 남은 확인이지 성공도
실패도 아니다. 실제 검토/전달은 기존 알림 계약을 따른다. 유료 API·신청·고객 연락은 사용하지 않는다.

## 데이터와 검증

- 목록/UTC/해시/receipt는 `data/raw/daily_research/`, 정상화 후보·관측 판·출처 상태는
  `data/daily-research.sqlite`에 둔다. 모두 Git 제외이며 기존 보고서/모델 DB를 열거나 수정하지 않는다.
- 요청 시작과 응답 확보 UTC를 분리한다. 초기 준비 실행의 이전 receipt는 실행 시작 시각만
  `acquired_at`에 기록했으므로 응답 완료 시각으로 재해석하지 않는다. 기존 receipt/최초 관찰은 보존하고
  새 획득부터 attempt_started_at/acquired_at을 분리한다. 캐시 재사용으로 획득 시각을 갱신하지 않는다.
- 후보 제목·발표일·신청기간·기관만 비교한다. 조회수·D-day 숫자·직원 이름·검색 form 상태로
  새 판을 만들지 않는다. 원문 날짜 미상은 확인일로 채우지 않고, 변경 관찰 시각과 구분한다.
- 실패한 출처의 후보/이전 판/마지막 성공을 보존한다. 출처 단위 중간 실패는 전체 변경을
  되돌리며, URL 이동 실패 후 이전 URL의 ETag를 새 URL에 적용하지 않는다.
- 성공 목록에서도 없어졌다는 이유로 후보를 삭제/종료하지 않는다. 목록에 없는 본문 정정은
  감지하지 못할 수 있으므로 선정한 공고와 중요한 보류 건의 상세/첨부는 따로 재확인한다.
- 2026-10-21 실제 수집:7목록172관측을 baseline으로 저장, 신규 출시 판정/알림0.
  재실행은7캐시 재사용,강제 HTTP 재확인에서도 새/변경0. 브라우저4경로·전 페이지/검색·첨부는 미완료다.
  최초 명령은 약6.8초였으며 계정 확인/네트워크 포함 한 번의 관찰값이다. 속도 보장이나 전수 조사 시간이 아니다.
- 관련 시험에서 실제 표 열/제목·원문 날짜, 최초 baseline, 재실행, 실제 정정/신규 URL,
  판 보존, 실패/빈 목록, 원자성, URL/ETag 결합, 캐시 시각, 출처 공정성/재수집 시각과 변경 시각 구분,
  브라우저 공백과 guard를 확인했다.
  초기 구현의 부분 변경/URL 실패2건을 재현한 뒤 소스 단위 rollback과 성공 URL 보존으로 수정했다.
  시험용 DB는 codex-temp-lifecycle 소유 scratch에서 종료 정리한다. 필수 검증 로그는
  `D:/9_codex_temp/2026-10-21/daily-research-preparation/`에 보존한다.

이 명령은 PC의 일일 조사 준비 도구다. GitHub의 사업 전수 자동 수집·공개 DB/페이지 연결이나
모든 자료의 본문/독립 검증을 구현했다는 뜻은 아니다. 운영 문서는 기사 원고/지식 검색의 신규 글로 발행하지 않는다.
