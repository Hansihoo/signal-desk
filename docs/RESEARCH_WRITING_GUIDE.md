[질문·근거·학습 결과 검토](../skills/research-teaching/references/substantive-review.md)를 적용한다.
독자의 핵심 질문마다 본문의 답 위치·근거·공백을 연결한다. 기술마다 고유한 원리와 실제 자료
해석이 있어야 하며, ‘조건 확인·검증·기록’의 반복만으로 보강됐다고 판정하지 않는다.
사용자가 승인한 독립 에이전트 검토에서는 수정 원고를 읽게 하고 지적을 고친 뒤 재판정한다.
전체 보강의 현재 범위와 실제 검증 결과는 [작업 상태](RESEARCH_AUTHORING_REPAIR.2026-10-09.md)에 남긴다.

2026-10-08부터 Signal Desk의 리서치 작성·보강·내용 검토에 적용한다.
이 문서는 작성 에이전트의 작업 기준이다. 독자에게 그대로 보여줄 목차나
모든 보고서에 강제할 양식이 아니다.

## 2026-10-10: 작성 목적 다음에 요약 배치하기

앞으로 새로 작성하는 공유용 페이지는 다음 순서로 시작한다.

1. 제목 아래에 어떤 목적으로 만든 문서인지 한두 문장으로 짧게 설명한다.
   독자의 어떤 문제나 판단을 돕기 위한 것인지 구체적으로 쓴다.
2. 바로 다음 본문 구역은 `요약`으로 표시하고 핵심 내용과 결론을 정리한다.
3. 요약 이후의 구성은 주제와 독자의 필요에 맞게 정한다. 목차, 개념 설명,
   비교표, 도해, 사례, 실습, 출처의 순서와 분량을 일률적으로 고정하지 않는다.

작성 목적은 “왜 이 문서를 만들었는가”에, 요약은 “핵심 내용과 결론이 무엇인가”에
답한다. 둘을 같은 소개 문장으로 반복하지 않는다. DevOps 문서의 장 수나
도구 카탈로그를 다른 주제의 필수 양식으로 삼지 않는다. 기존 페이지를 일괄
재작성하는 규칙은 아니며, 앞서 정한 출처와 검토 기준은 유지한다.

예시 작성 목적: “기존 Jenkins를 사용하는 C++ 팀이 검사 결과를 보관하고,
검사한 파일을 릴리스하는 절차를 정할 수 있도록 구축 방법을 정리했다.”

검토할 때는 첫 화면만 읽어 작성 목적을 알 수 있는지, 그다음 구역이 요약인지,
요약에서 핵심 내용과 결론을 파악할 수 있는지 각각 확인한다. 본문 구성은
이 고정된 앞부분 이후에 필요한 설명을 충분히 제공하는지로 판단한다.

## 2026-10-10: 가운데점으로 단어나 동작을 묶지 않기

새로 작성하거나 수정하는 제목, 요약, 본문, 표와 도구 설명에는 가운데점으로
단어를 압축해 나열하지 않는다. 점을 공백으로 지우는 것으로 끝내지 않는다.
병렬 항목은 쉼표나 자연스러운 연결어로 구분하고, 동작은 누가 무엇을 어떤
순서로 하는지 문장으로 쓴다. 원문 코드, URL과 기존 분류 식별자는 보존한다.

- 피할 표현: “누가 어떤 코드와 결과물을 검사·승인·반영했는지”
- 사용할 표현: “누가 코드를 검사했고, 어떤 결과물을 승인해 실제 환경에 반영했는지”
- 피할 표현: “개발·QA·운영이 공동 책임”
- 사용할 표현: “개발 담당자는 코드를 수정하고 QA는 검사한다. 운영 담당자는 승인된 파일을 배포한다.”

## 2026-10-10: 추상적 정의를 구체적인 업무로 설명하기

사용자는 DevOps의 정의인 “기능의 전달과 서비스의 안정성을 함께 책임지는 문화와 실천”을
이해하기 어렵다고 지적했다. 회사 공유 보고서의 문체는 어려운 명사를 쓰는 것이 아니다.
정의와 요약에는 누가 무엇을 하는지, 어떤 상황에서 쓰는지와 확인할 결과를 평이하게 쓴다.

- “문화와 실천”, “가치 전달”, “공동 책임” 같은 표현만으로 정의를 끝내지 않는다.
  필요하다면 코드 검사 항목·배포 절차·장애 담당자처럼 실제 결정과 행동으로 풀어 쓴다.
- 첫 정의 다음에 해당 주제의 사례를 붙인다. DevOps는 무료배송 기준을 바꾼 뒤
  금액별 계산을 검사하고, 배포 후 주문 오류를 확인하며, 오류를 다음 검사에 추가하는 과정으로 설명한다.
- 형용사나 명사를 다른 추상어로 바꾸는 데서 끝내지 않는다. “누가 어떤 작업을 하나?”에
  답하지 못하는 문장은 구체적인 작업·조건·결과를 보충한다. 용어를 생략해서 의미를 왜곡하지 않는다.

기술 용어 자체를 일괄 금지하는 기준은 아니다. 필요한 용어는 먼저 뜻과 작동을 설명한다.
문장만 다듬어 원문의 범위, 근거 수준, 조건이나 수치가 달라지지 않았는지도 따로 확인한다.

완료됐다는 이유로 현재 글을 승인된 교재의 기준으로 복제하지 않는다.

무엇을 조사하고 새 주제를 어떻게 발견할지는 [AI 조사 운영](AI_RESEARCH_OPERATIONS.md)과
[출처 목록](AI_RESEARCH_SOURCES.md)을 따른다. 독자는 개발자와 관리자다. 기술을 배우는 글뿐 아니라
도입·조직·인력시장 판단을 돕는 글도 포함한다. 목적에 맞는 설명과 사례를 선택하며,
모든 글에 SDK 구현을 강제하지 않는다. 실제 수집·검토 날짜와 범위는
[검토 기록](ai/AI_RESEARCH_REVIEW_LOG.md)에 남긴다.

## 개발 동향의 목적: AI를 실제 작업에 활용하기

2026-10-08 후속 사용자 요구: 개발 동향은 AI를 활용하는 방법을 계속 수집하고
독자가 필요할 때 배워 사용하는 지식베이스다. 새 기능을 알아보거나 역할을
설명하는 수준에서 끝나면 이 목적을 달성하지 못한다.

먼저 독자가 끝낼 구체적인 작업과 그 결과물을 정한다. 예를 들어 'MCP Apps의
호스트·서버를 구분한다'는 중간 학습 목표다. 최종 목적에는 어떤 목록을 비교하고,
어떤 환경에서 시작하며, 자기 데이터로 어떻게 바꾸고, 성공을 무엇으로 확인하는지가
있어야 한다. 준비된 기능을 사용하는 독자와 기능을 직접 구현하는 독자의 경로도
구분한다. AI 활용이라는 말만으로 SDK 구현이 필요한 독자로 가정하지 않는다.

기초 개념과 작동 이유를 충분히 설명하되 하나의 완성된 예제를 따라 연결한다.
실습을 제공한다면 행동과 관찰할 결과를 따로 제시하고, 긴 원리 설명은 실습을
읽는 흐름과 구분해 찾을 수 있게 둔다. 설명만 길게 늘리거나 매 문단에 행동을
강제로 넣는 방식은 쓰지 않는다. 필요에 맞는 장 구성은 원고를 쓴 뒤 선택한다.

이전 MCP Apps 3차와 당시 개선 원고는 사용자가 활용 교재로 부족하다고 평가했다.
승인된 완성 교재의 문체·깊이 기준으로 복제하지 않는다. 2026-10-08에는 아래 절차를
적용해 작성 보고서 20편의 새 판을 게시했다. [보강 기록](RESEARCH_REPAIR.2026-10-08.md)은
근거·이해 가능성 자체검토와 출력 검증을 구분한다. 실제 독자 승인이나 전 조사 범위의
완료를 뜻하지 않으며, 이후 원고도 목적과 최신 근거를 다시 검토한다.

## 글을 쓰기 전에 정할 것

교재형 글은 선행 개념의 순서를 확인한다. 먼저 익숙한 상황과 값으로 문제를
설명하고, 그 문제에서 새 개념이 하는 일을 가르친 뒤 기술 이름·구조·코드를 연결한다.
새 약어를 풀어 쓰는 것만으로 선행 지식의 공백이 해결되지는 않는다.

목적은 자료 요약, 표 생성, 제목 작성이 아니라 **독자에게 생겨야 할 변화**다.
먼저 아래 내용을 짧은 편집 메모에 적는다. 모르는 독자의 수준은 가정임을
밝히고, 대화에서 이미 확인한 필요를 우선한다.

| 질문 | 작성할 내용 |
| --- | --- |
| 누가 읽는가 | 주제와의 거리, 현재 알고 있는 것, 새로 설명해야 할 것 |
| 왜 읽는가 | 이해하려는 문제 또는 내려야 할 결정 하나 |
| 읽은 뒤 무엇이 가능한가 | 구분·설명·선택·실행처럼 확인 가능한 결과 |
| 무엇을 다룰 것인가 | 그 결과에 필요한 범위와 선행 개념 |
| 어떤 근거가 필요한가 | 기능, 수치, 적용 조건, 비교를 지지할 원문 |
| 어떻게 확인할 것인가 | 다른 사례에 적용하는 질문 또는 관찰할 실행 결과 |

예: MCP Apps의 역할을 모르는 독자가 공고 후보를 비교하는 업무에 이 기술을
쓸 이유와 시작 경로를 고르고, 설명된 사례의 입력·조회·화면 결과를 추적한 뒤
자기 목록에 적용할 변경점을 찾도록 쓴다. 역할을 설명하는 것은 이 작업을 위한
중간 단계다. 예시를 실제로 실행시키는 경로를 제공하려면 현재 지원 환경·준비물·
실행 절차·예상 결과를 확인한다. 이것이 없는 원고는 원리 설명으로 상태를 남긴다.

‘초급~중급 개발자’라는 범위만으로 API, JSON, 비동기 처리, MCP를 이미
안다고 가정하지 않는다. 필요한 개념은 설명하거나 정확한 선행 학습으로 연결한다.

## 목적에 맞게 글의 성격을 고르기

| 독자의 질문 | 중심 내용 | 완료를 확인하는 방법 |
| --- | --- | --- |
| 무엇이 바뀌고 내 작업에 어떤 영향이 있나 | 이전 상태, 변화, 해당 대상, 영향, 대응 시점 | 자신의 사용 여부와 다음 점검을 정할 수 있음 |
| 이것은 무엇이고 왜 필요한가 | 익숙한 상황, 개념, 작동 이유, 구체적 사례, 한계 | 새로운 사례의 동작을 자기 말로 설명함 |
| 어느 대안이 내 조건에 맞나 | 같은 비교 기준, 적용 조건, 비용·제약, 선택 이유 | 주어진 조건으로 대안을 고르고 이유를 말함 |
| 따라 하면서 익히려면 무엇을 하나 | 준비물, 순서, 입력, 예상 출력, 오류 관찰 | 실제 결과를 재현하고 어느 단계에서 틀렸는지 찾음 |
| 신청·참여할 수 있나 | 대상, 현재 접수 상태, 자격, 제외 조건, 제출물 | 해당·비해당·추가 확인을 구분하고 준비물을 정함 |
| 이 수치·사례는 무엇을 알려주나 | 측정 대상·기간·단위, 관찰과 해석, 적용 한계 | 수치의 의미와 이 자료로 알 수 없는 것을 구분함 |

설명 글과 실습 글의 역할은 다르다. 설명은 관계와 이유를 풀어내고, 실습은
독자가 행동한 뒤 확인할 결과를 제공한다. 하나의 보고서에 둘 다 필요하면
단위를 나누어 연결한다. 단순히 명령어를 넣었다고 실습이 완성되는 것은 아니다.
이 구분은 [Diátaxis의 설명](https://diataxis.fr/explanation/)과
[튜토리얼](https://diataxis.fr/tutorials/)을 참고한 프로젝트 편집 선택이다.

## 원문에서 의미를 보존하기

자료를 읽을 때 제목부터 만들지 않는다. 독자의 질문에 답하는 근거를 먼저
확보하고, 아래 항목이 필요한 주장에 함께 남긴다.

- 누가 무엇을 하는가: 제공자·실행자·요청자·결과 수신자를 구분한다.
- 언제, 누구에게 적용되는가: 확인일, 발표일, 종료일, 지역·계정·버전 조건.
- 무엇을 측정했는가: 기간·표본·분모·단위와 출처의 자체 공개 여부.
- 무엇을 관찰했고 무엇을 해석했는가: 공식 기능, 편집 판단, 가상 예시를 구분한다.
- 어떤 제한이 결론을 바꾸는가: 적용 제외, 필수 준비, 비교하지 못한 부분.

출처 링크가 붙어 있는 것과 그 출처가 문장을 뒷받침하는 것은 별개다.
원문의 주어·목적어·인과관계를 요약 과정에서 바꾸지 않는다. 예를 들어
‘서버가 화면을 제공하고 호스트가 읽는다’를 ‘서버가 읽는 화면’으로 줄이면
구조가 바뀐다. 규격은 실제 동작의 보장, 최대 지원액은 확정 지급액,
한 회사의 성장과 제품 전략은 검증된 성장 원인으로 바꾸지 않는다.

동적 규정·모델명·가격·프로그램 상태는 보강 시 공식 자료를 다시 확인한다.
개념 문장을 고쳤다는 이유로 재확인하지 않은 다른 표의 확인일을 올리지 않는다.

## 독자의 질문 순서로 원고 쓰기

개념 설명이 필요한 글에서는 독자가 겪는 상황부터 시작한다. 새 용어를
그 상황의 구체적 역할과 연결한 뒤, 한 사례를 입력에서 결과까지 이어 쓴다.
각 단계에서 ‘누가, 어떤 값으로, 무엇을 하고, 무엇이 달라지는지’를 밝힌다.
필요한 이유와 대안의 차이를 설명한 후에 도입 판단을 제시한다.

‘도구 호출·RAG·상태·평가’를 나열하는 대신 같은 공고 비교 앱을 따라갈 수 있다.
조회 함수는 조건에 맞는 공고를 찾고, 문서 검색은 공고 본문에서 신청 조건의
근거를 찾으며, 평가는 반환된 공고와 답변이 그 근거에 맞는지 확인한다.
단계가 바뀌어도 사용자의 요청과 샘플 데이터를 유지하면 역할 차이가 드러난다.

압축어가 아니라 완결된 문장으로 설명한다. 약어의 영어 원형만 제시하지 말고
이 사례에서 그 개념이 맡는 일을 말한다. 새 개념의 정의가 또 다른 미설명
약어에 의존하면 그 선행 개념도 보완한다. 같은 정의를 반복하는 대신 다음
문단에서 왜 그렇게 동작하는지 또는 무엇을 확인해야 하는지 전진한다.

표는 이미 설명한 기준의 비교·확인에 쓴다. 표가 처음 등장한 개념의 유일한
설명이어서는 안 된다. 숫자에는 읽는 방법을, 흐름도에는 각 이동 값의 의미를
붙인다. 시각 자료가 결론을 어떻게 지지하는지 본문에서 연결한다.

## 짧은 메인과 충분한 보고서

메인은 독자가 읽을 보고서를 고를 수 있게 핵심 변화·문제·대상 조건을 짧게
전달한다. 보고서는 선택한 내용을 혼자 이해할 수 있을 만큼 풀어 쓴다.
메인의 분량 기준을 본문에 적용하지 않는다. 고정 글자 수나 항목 수로
필수 설명을 자르지 않는다.

펼치기는 상세 절차·추가 사례·사양·선택적 심화에 사용한다. 제목을 이해하는 데
필요한 정의, 결론의 이유, 결정적인 자격·제약은 기본 읽기 경로에 둔다.
처음 읽는 사람이 모든 펼치기를 열어야만 첫 문장을 이해한다면 배치가 잘못됐다.
펼친 내용은 요약의 반복이 아니라 빠진 관계와 사례를 설명해야 한다.

현재 Editorial의 `요약 → 데이터 → 결과 → 해설` 순서와 블록 개수는 의미 품질을
보장하지 않는다. 원고를 먼저 완성하고 기존 데이터 필드에 의미를 유지하며
옮긴다. 필요한 설명을 현재 필드로 자연스럽게 표현할 수 없으면 원고를 보존하고
렌더링 개선을 별도 작업으로 기록한다. 원고를 양식에 맞춰 다시 축약하지 않는다.

## 실습이라면 확인 가능한 왕복 제공

실습에는 준비 환경과 버전, 입력, 단계별 예상 출력, 정상·실패 판정, 다음 단계가
필요하다. 개념 예시나 의사 코드는 그렇게 표시한다. 실행하지 않은 코드를
실행 검증한 튜토리얼로 부르지 않는다. 유료 호출·계정 준비가 필요한 경우
독자가 선택하기 전에 알 수 있게 한다.

입력과 도구 정의는 서로 맞아야 한다. 날짜 조건을 요구하는 예시라면 그 조건을
받을 인자 또는 필터 단계가 있어야 한다. 반환 필드, 화면 필드, 인용하는 자료 ID도
일치해야 한다. 연결 확인용 echo 결과와 실제 검색·문서 분석 결과를 구분한다.
‘정확도를 확인한다’고 끝내지 말고 무엇과 비교하며 어떤 경우 실패인지 보여준다.

## 에이전트의 작성 절차와 게시 판단

1. **독자 작업 정의:** 업무 문제, 기존 지식, 끝낼 작업, 확인할 결과를 작성한다.
   'MCP 이해하기', 'RAG 알아보기'처럼 기술 이름만 쓰면 다시 구체화한다.
2. **필요한 근거 조사:** 이 작업을 할 수 있는 현재 도구·기능, 시작 조건, 제약,
   공식 예제를 확인한다. 원문 요약을 바로 게시용 문장으로 바꾸지 않는다.
3. **완성된 사례 구성:** 실제 샘플 값과 중간 결과를 고정한다. 어느 입력이 어떤
   처리를 거쳐 어떤 출력에 대응하는지 끝까지 보여주고, 필요한 개념을 그 관계로
   설명한다. 가상 사례·개념 코드·실행 확인한 실습은 구분한다.
4. **학습과 적용 작성:** 왜 쓰는지, 어떻게 동작하는지, 어떻게 시작하는지,
   자기 작업으로 바꾸려면 무엇이 달라지는지 설명한다. 설명형 학습에는 풀이가
   있는 변형 문제를, 실습에는 행동·예상 출력·정상/실패 판정을 제공한다.
5. **검토 후 재작성:** 아래 질문에 본문 위치를 인용해 답한다. 필요한 답이
   본문에 없으면 누락으로 기록하고 원고를 보강한다. 검토자 자신의 상식으로
   빈칸을 메워 통과시키지 않는다. 어려운 용어의 정의만 반복해 해결하지 않는다.
6. **표현과 게시:** 내용이 충족된 뒤 메인 요약과 HTML을 만든다. 설명 필드를
   모두 채웠거나 테스트가 통과했다고 교재 완성으로 처리하지 않는다. 검수 결과와
   실행 확인 범위를 기록하고, 필요한 본문은 펼치기 안에 숨기지 않는다.

| 검토 질문 | 원고가 보여줘야 할 근거 |
| --- | --- |
| 이 방법으로 내 어떤 작업이 나아지는가 | 구체적인 문제·완성 결과·적합하지 않은 경우 |
| 어디서 어떻게 시작하는가 | 선택한 사용/구현 경로와 확인한 환경·준비물·첫 행동 |
| 각 부분이 왜 필요한가 | 예시 값과 연결된 개념·처리 원리·선행 지식 |
| 한 사례의 입력부터 결과까지 따라갈 수 있는가 | 실제 샘플 값·중간 변화·출력과 그 의미 |
| 내 자료로 바꾸려면 무엇을 바꾸는가 | 다른 입력으로의 변형 예시와 풀이·변경점 |
| 틀렸을 때 무엇을 확인하는가 | 관찰할 증상·확인 순서·실패 조건 |

이 표는 게시용 목차나 점수표가 아니다. 모든 주제에 실행 실습을 강제하지 않는다.
개념 교재에도 끝까지 풀어 준 사례와 새로운 상황에 적용하는 설명이 필요하다.
실습을 약속한 글은 재현 경로가 빠지면 '실습 초안'으로 남긴다. 실행해 보지 않은
단계를 검증 완료로 표시하거나 독자 사용성 시험을 했다고 주장하지 않는다.

자동화를 구성할 때는 프로젝트 AGENTS에 위 목적과 필수 읽기를 두고, 작성 스킬에는
단계별 입력·산출물·누락 시 재작성 규칙을 둔다. 지식베이스는 출처와 기능 조건,
끝까지 풀어 준 예제, 사용자 검토를 받은 원고, 실패한 문장의 이유를 보존한다.
기술 정리 역할과 집필·검토 역할은 별도 작업 단계로 수행한다. 여러 에이전트를
자동으로 만드는 규칙은 아니며, 같은 에이전트의 별도 검토 과정으로도 수행한다.

Google의 [독자 기준](https://developers.google.com/tech-writing/one/audience)은
업무에 필요한 지식과 독자가 이미 가진 지식의 차이를 설명 범위로 삼는다.
Diátaxis의 [실습 기준](https://diataxis.fr/tutorials/)은 구체적인 행동과 예상 결과를
연결한다. [OpenAI의 스킬 문서](https://developers.openai.com/codex/skills)는
재사용할 작업 절차를 지침·참고자료로 묶고 명시적인 입력·출력으로 설계하도록
안내한다. 세 원문의 적용 절차와 위 검토 기준은 이 프로젝트의 편집 판단이다.

## 제목·요약만으로 무엇을 배우는지 알 수 있는가

2026-10-09 음성 보고서의 사용자 거부는 앞선 독립 Pass가 첫 화면의 이해와 자연스러움을
충분히 검증하지 못했음을 보여준다. [수정 기록](VOICE_REPORT_REPAIR.2026-10-09.md)과
[구체적인 회귀 사례](../skills/research-teaching/references/substantive-review.md#첫-화면과-비교-기준의-회귀-사례)를 따른다.
첫 화면 검토에서는 본문을 실제로 제외한다. 명사형 소개를 완결된 문장으로 바꾸고, 독자가
하려는 작업과 실제 비교 대상을 먼저 밝힌다. 구현 구조와 제품명을 같은 종류의 행으로 섞지 않는다.
성능·비용·난이도 비교를 약속할 때는 실측·문헌 근거·설계 해석을 구분한다.

제목에는 기술·주제 이름과 평이한 기능·변화·문제를 함께 담는다. 이름이 빠져
무엇에 관한 글인지 알 수 없는 제목, 낯선 이름만 나열한 제목은 보강한다.
요약은 본문 밖에서 읽어도 대상, 하는 일, 구체적인 쓰임과 중요한 조건이 전달되어야 한다.
본문의 B·호스트·UI 리소스·문맥을 설명 없이 가져오지 않는다.

본문을 읽은 지식으로 요약의 빈칸을 채우지 않는다. 제목·요약만 보고 다시 설명한 답과
근거 문장을 남기고, 알 수 없는 부분을 실제로 고친다. 본문은 별도로 개념 순서,
한 사례의 전체 과정과 다른 조건의 문제를 검토한다. 검사표 점수나 글자 수로 대체하지 않는다.

용어집, 출처 모음, 글자 수 지침만 쌓지 않는다.

원문을 재확인하고 재사용한다. 예시 문장은 이번 독자 목적에 맞춘 사례다.

## 내용 검토와 기술 검증을 분리해서 기록

게시 전에는 원고만으로 아래 질문에 답할 수 있는지 검토한다.

1. 독자가 해결할 질문에 이 글이 실제로 답했는가?
2. 선행 지식을 모르면 어느 문장에서 막히며, 그 부분을 설명했는가?
3. 주어·대상·조건·단위가 원문과 같은가? 인과관계를 과장하지 않았는가?
4. 한 예시의 입력·처리·출력이 연결되고 서로 모순되지 않는가?
5. 결론이 왜 나오는지 설명하며 적용되지 않는 조건도 구분했는가?
6. 처음의 예시와 다른 상황에 독자가 이 개념을 적용할 수 있는가?
7. 원문 링크는 근거 확인·심화 학습을 돕는가? 빠진 본문 설명을 대신하지 않는가?

각 질문은 통과 문구를 붙이는 체크박스가 아니라 실제 원고를 고칠 기준이다.
막힌 문장과 수정 이유를 기록한다. 새 사례에 대한 예상 답은 근거와 함께
작성하되 실제 독자 시험을 하지 않았다면 독자 검증 완료라고 쓰지 않는다.

현재 `validate_report`는 형식·출처 ID·자료 타입을, `review`는 주택 브리핑의
운영·출력 상태를 검사한다. 테스트 통과·출처 수·학습 장 수·모바일 넘침 없음은
독자의 이해를 증명하지 않는다. 자동 검사에는 구조적으로 확인 가능한 부분만
맡기고 사실 의미·논리·설명 충실도는 원문과 원고를 읽어 검토한다.

보고서 수정 게시 시에는 새 immutable batch와 같은 보고서 ID로 이력을
남긴다. 앞선 판을 덮어쓰지 않는다. 렌더링·링크·모바일 검증은 내용 검토와
함께 수행하되 각각의 결과를 구분해 기록한다.
