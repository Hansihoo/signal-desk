# 독자가 이해하고 판단할 수 있는 리서치 글

2026-10-08부터 Signal Desk의 리서치 작성·보강·내용 검토에 적용한다.
이 문서는 작성 에이전트의 작업 기준이다. 독자에게 그대로 보여줄 목차나
모든 보고서에 강제할 양식이 아니다.

## 글을 쓰기 전에 정할 것

목적은 자료 요약, 표 생성, 제목 작성이 아니라 **독자에게 생겨야 할 변화**다.
먼저 아래 내용을 짧은 편집 메모에 적는다. 모르는 독자의 수준은 가정임을
밝히고, 대화에서 이미 확인한 필요를 우선한다.

| 질문 | 작성할 내용 |
| --- | --- |
| 누가 읽는가 | 주제와의 거리, 현재 알고 있는 것, 새로 설명해야 할 것 |
| 왜 읽는가 | 이해하려는 문제 또는 내려야 할 결정 하나 |
| 읽은 뒤 무엇이 가능한가 | 구분·설명·선택·실행처럼 확인 가능한 결과 |
| 무엇을 다룰 것인가 | 그 결과에 필요한 범위와 선행 개념 |
| 어떤 근거가 필요한가 | 기능, 수치, 적용 조건, 비교를 지지할 원문 |
| 어떻게 확인할 것인가 | 다른 사례에 적용하는 질문 또는 관찰할 실행 결과 |

예: MCP Apps 글은 웹페이지를 본 적 있지만 MCP의 역할을 모르는 독자가
‘공고 표에서 상세보기를 누르면 누가 요청하고 누가 결과를 보여주는지’를
설명하고, 자신의 비교 작업에 화면이 필요한지 판단하도록 쓴다. 사양의
모든 필드를 외우거나 서버를 배포하는 것은 이 글의 목표에 포함하지 않는다.
목표가 구현이라면 준비 환경과 실행 절차를 갖춘 별도 실습이 필요하다.

‘초급~중급 개발자’라는 범위만으로 API, JSON, 비동기 처리, MCP를 이미
안다고 가정하지 않는다. 필요한 개념은 설명하거나 정확한 선행 학습으로 연결한다.

## 목적에 맞게 글의 성격을 고르기

| 독자의 질문 | 중심 내용 | 완료를 확인하는 방법 |
| --- | --- | --- |
| 무엇이 바뀌고 내 작업에 어떤 영향이 있나 | 이전 상태, 변화, 해당 대상, 영향, 대응 시점 | 자신의 사용 여부와 다음 점검을 정할 수 있음 |
| 이것은 무엇이고 왜 필요한가 | 익숙한 상황, 개념, 작동 이유, 구체적 사례, 한계 | 새로운 사례의 동작을 자기 말로 설명함 |
| 어느 대안이 내 조건에 맞나 | 같은 비교 기준, 적용 조건, 비용·제약, 선택 이유 | 주어진 조건으로 대안을 고르고 이유를 말함 |
| 따라 하면서 익히려면 무엇을 하나 | 준비물, 순서, 입력, 예상 출력, 오류 관찰 | 실제 결과를 재현하고 어느 단계에서 틀렸는지 찾음 |
| 신청·참여할 수 있나 | 대상, 현재 접수 상태, 자격, 제외 조건, 제출물 | 해당·비해당·추가 확인을 구분하고 준비물을 정함 |
| 이 수치·사례는 무엇을 알려주나 | 측정 대상·기간·단위, 관찰과 해석, 적용 한계 | 수치의 의미와 이 자료로 알 수 없는 것을 구분함 |

설명 글과 실습 글의 역할은 다르다. 설명은 관계와 이유를 풀어내고, 실습은
독자가 행동한 뒤 확인할 결과를 제공한다. 하나의 보고서에 둘 다 필요하면
단위를 나누어 연결한다. 단순히 명령어를 넣었다고 실습이 완성되는 것은 아니다.
이 구분은 [Diátaxis의 설명](https://diataxis.fr/explanation/)과
[튜토리얼](https://diataxis.fr/tutorials/)을 참고한 프로젝트 편집 선택이다.

## 원문에서 의미를 보존하기

자료를 읽을 때 제목부터 만들지 않는다. 독자의 질문에 답하는 근거를 먼저
확보하고, 아래 항목이 필요한 주장에 함께 남긴다.

- 누가 무엇을 하는가: 제공자·실행자·요청자·결과 수신자를 구분한다.
- 언제, 누구에게 적용되는가: 확인일, 발표일, 종료일, 지역·계정·버전 조건.
- 무엇을 측정했는가: 기간·표본·분모·단위와 출처의 자체 공개 여부.
- 무엇을 관찰했고 무엇을 해석했는가: 공식 기능, 편집 판단, 가상 예시를 구분한다.
- 어떤 제한이 결론을 바꾸는가: 적용 제외, 필수 준비, 비교하지 못한 부분.

출처 링크가 붙어 있는 것과 그 출처가 문장을 뒷받침하는 것은 별개다.
원문의 주어·목적어·인과관계를 요약 과정에서 바꾸지 않는다. 예를 들어
‘서버가 화면을 제공하고 호스트가 읽는다’를 ‘서버가 읽는 화면’으로 줄이면
구조가 바뀐다. 규격은 실제 동작의 보장, 최대 지원액은 확정 지급액,
한 회사의 성장과 제품 전략은 검증된 성장 원인으로 바꾸지 않는다.

동적 규정·모델명·가격·프로그램 상태는 보강 시 공식 자료를 다시 확인한다.
개념 문장을 고쳤다는 이유로 재확인하지 않은 다른 표의 확인일을 올리지 않는다.

## 독자의 질문 순서로 원고 쓰기

개념 설명이 필요한 글에서는 독자가 겪는 상황부터 시작한다. 새 용어를
그 상황의 구체적 역할과 연결한 뒤, 한 사례를 입력에서 결과까지 이어 쓴다.
각 단계에서 ‘누가, 어떤 값으로, 무엇을 하고, 무엇이 달라지는지’를 밝힌다.
필요한 이유와 대안의 차이를 설명한 후에 도입 판단을 제시한다.

‘도구 호출·RAG·상태·평가’를 나열하는 대신 같은 공고 비교 앱을 따라갈 수 있다.
조회 함수는 조건에 맞는 공고를 찾고, 문서 검색은 공고 본문에서 신청 조건의
근거를 찾으며, 평가는 반환된 공고와 답변이 그 근거에 맞는지 확인한다.
단계가 바뀌어도 사용자의 요청과 샘플 데이터를 유지하면 역할 차이가 드러난다.

압축어가 아니라 완결된 문장으로 설명한다. 약어의 영어 원형만 제시하지 말고
이 사례에서 그 개념이 맡는 일을 말한다. 새 개념의 정의가 또 다른 미설명
약어에 의존하면 그 선행 개념도 보완한다. 같은 정의를 반복하는 대신 다음
문단에서 왜 그렇게 동작하는지 또는 무엇을 확인해야 하는지 전진한다.

표는 이미 설명한 기준의 비교·확인에 쓴다. 표가 처음 등장한 개념의 유일한
설명이어서는 안 된다. 숫자에는 읽는 방법을, 흐름도에는 각 이동 값의 의미를
붙인다. 시각 자료가 결론을 어떻게 지지하는지 본문에서 연결한다.

## 짧은 메인과 충분한 보고서

메인은 독자가 읽을 보고서를 고를 수 있게 핵심 변화·문제·대상 조건을 짧게
전달한다. 보고서는 선택한 내용을 혼자 이해할 수 있을 만큼 풀어 쓴다.
메인의 분량 기준을 본문에 적용하지 않는다. 고정 글자 수나 항목 수로
필수 설명을 자르지 않는다.

펼치기는 상세 절차·추가 사례·사양·선택적 심화에 사용한다. 제목을 이해하는 데
필요한 정의, 결론의 이유, 결정적인 자격·제약은 기본 읽기 경로에 둔다.
처음 읽는 사람이 모든 펼치기를 열어야만 첫 문장을 이해한다면 배치가 잘못됐다.
펼친 내용은 요약의 반복이 아니라 빠진 관계와 사례를 설명해야 한다.

현재 Editorial의 `요약 → 데이터 → 결과 → 해설` 순서와 블록 개수는 의미 품질을
보장하지 않는다. 원고를 먼저 완성하고 기존 데이터 필드에 의미를 유지하며
옮긴다. 필요한 설명을 현재 필드로 자연스럽게 표현할 수 없으면 원고를 보존하고
렌더링 개선을 별도 작업으로 기록한다. 원고를 양식에 맞춰 다시 축약하지 않는다.

## 실습이라면 확인 가능한 왕복 제공

실습에는 준비 환경과 버전, 입력, 단계별 예상 출력, 정상·실패 판정, 다음 단계가
필요하다. 개념 예시나 의사 코드는 그렇게 표시한다. 실행하지 않은 코드를
실행 검증한 튜토리얼로 부르지 않는다. 유료 호출·계정 준비가 필요한 경우
독자가 선택하기 전에 알 수 있게 한다.

입력과 도구 정의는 서로 맞아야 한다. 날짜 조건을 요구하는 예시라면 그 조건을
받을 인자 또는 필터 단계가 있어야 한다. 반환 필드, 화면 필드, 인용하는 자료 ID도
일치해야 한다. 연결 확인용 echo 결과와 실제 검색·문서 분석 결과를 구분한다.
‘정확도를 확인한다’고 끝내지 말고 무엇과 비교하며 어떤 경우 실패인지 보여준다.

## 작성 지식베이스에 남길 내용

새 주제의 편집 메모는 관련 보고서·검토 문서에 아래 정보를 남긴다. 단순
용어집, 출처 모음, 글자 수 지침만 쌓지 않는다.

| 항목 | 저장할 지식 |
| --- | --- |
| 독자의 질문 | 해당 글이 해결할 질문과 선행 지식 가정 |
| 개념 관계 | 기존 개념과의 차이, 역할과 데이터 이동 |
| 의미 근거 | 주장별 원문 위치·적용 조건·확인일 |
| 끝까지 이어지는 예시 | 입력, 중간 값, 출력, 정상·실패 이유 |
| 발견한 실패 | 원고의 어떤 표현이 무슨 오해를 만들었는지 |
| 개선 원고 | 실제로 고친 문단과 독자가 대답할 수 있어야 할 질문 |
| 보강 상태 | 진단·원고·사실 확인·실행 검증·게시 중 완료한 범위 |

현재 기준 사례는 [16편 내용 검토](RESEARCH_CONTENT_REVIEW.2026-10-08.md)와
[MCP Apps·도구 호출 개선 원고](RESEARCH_WRITING_EXAMPLES.md)다. 날짜가 붙은
기능·규정은 원문을 재확인하고 재사용한다. 예시 문장은 범용 정답이 아니라
이번 독자 목적에 맞춘 사례다.

## 내용 검토와 기술 검증을 분리해서 기록

게시 전에는 원고만으로 아래 질문에 답할 수 있는지 검토한다.

1. 독자가 해결할 질문에 이 글이 실제로 답했는가?
2. 선행 지식을 모르면 어느 문장에서 막히며, 그 부분을 설명했는가?
3. 주어·대상·조건·단위가 원문과 같은가? 인과관계를 과장하지 않았는가?
4. 한 예시의 입력·처리·출력이 연결되고 서로 모순되지 않는가?
5. 결론이 왜 나오는지 설명하며 적용되지 않는 조건도 구분했는가?
6. 처음의 예시와 다른 상황에 독자가 이 개념을 적용할 수 있는가?
7. 원문 링크는 근거 확인·심화 학습을 돕는가? 빠진 본문 설명을 대신하지 않는가?

각 질문은 통과 문구를 붙이는 체크박스가 아니라 실제 원고를 고칠 기준이다.
막힌 문장과 수정 이유를 기록한다. 새 사례에 대한 예상 답은 근거와 함께
작성하되 실제 독자 시험을 하지 않았다면 독자 검증 완료라고 쓰지 않는다.

현재 `validate_report`는 형식·출처 ID·자료 타입을, `review`는 주택 브리핑의
운영·출력 상태를 검사한다. 테스트 통과·출처 수·학습 장 수·모바일 넘침 없음은
독자의 이해를 증명하지 않는다. 자동 검사에는 구조적으로 확인 가능한 부분만
맡기고 사실 의미·논리·설명 충실도는 원문과 원고를 읽어 검토한다.

보고서 수정 게시 시에는 새 immutable batch와 같은 보고서 ID로 이력을
남긴다. 앞선 판을 덮어쓰지 않는다. 렌더링·링크·모바일 검증은 내용 검토와
함께 수행하되 각각의 결과를 구분해 기록한다.
