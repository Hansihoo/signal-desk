# 이해하고 활용할 수 있는 리서치 글

독자가 글의 대상과 쓰임을 알아보고, 내용을 자기 말로 설명하거나 자기 조건에 적용할 수 있게 쓴다.
정보가 부족하면 조사해서 채운다. 이해의 빈칸을 문체 수정·요약·장 수 증가로 대체하지 않는다.

## 시작점과 범위

기존 원고를 실제 읽고, 독자가 막히는 문장과 빠진 설명을 확인한다.
대화에 이미 나온 독자·목적·형식을 사용한다. 같은 질문을 다시 요구하지 않는다.
독자의 선행 지식은 직함보다 해당 주제와의 거리를 기준으로 잡는다.
‘개발자’라는 이유로 MCP·API·JSON·RAG를 이미 안다고 가정하지 않는다.

Signal Desk에서는 프로젝트의 작성 기준·조사 운영·데이터 계약을 함께 읽는다.
이 스킬은 집필 판단을 보완하며 새 수집기, 도구 권한, 예약·배포 허가를 만들지 않는다.
글을 고칠 때 웹 디자인은 별도 요청이 없다면 유지한다.

## 초안 전에 확보할 것

정보가 의미 없다는 피드백이나 여러 글의 일괄 보강에서는
[질문·근거·학습 결과 검토](references/substantive-review.md)를 읽는다.
형식을 갖춘 기존 글을 완성된 교재로 복제하지 않는다. 같은 주제라도 기술 설명,
실행 실습, 시장 판단에 필요한 자료와 합격 조건은 다르다.

작업 메모에 독자의 질문, 현재 아는 것, 새로 배울 것, 끝에 가능한 설명·선택·행동을 적는다.
‘기술 이해하기’만 적지 말고 구체적인 문제와 답할 질문을 잡는다.
학습 목표 사이의 선행 관계를 찾아 먼저 설명할 개념을 정한다.

기능·관계·지원 조건·수치의 원문 근거와 실제 확인 날짜를 모은다.
어떤 문장을 쓰려는데 근거가 부족하면 그 질문을 조사한다. 규격과 구현, 공급사 주장과
독립 검증, 측정 기간과 수집일을 구분한다. 조사하지 못한 조건은 불명확한 권고로 바꾸지 않는다.

설명, 따라 하는 실습, 업무 절차, 비교·시장 분석 중 독자에게 필요한 글을 선택한다.
‘교과서처럼’은 모든 글에 SDK 설치를 넣으라는 뜻이 아니다. 실행 실습을 약속하면
준비물·환경·행동·예상 결과·실패 진단을 실제로 확인한다.

## 본문 작성

익숙한 문제에서 출발해 필요한 개념을 소개하고, 관계와 작동 이유를 풀어 준다.
정의는 영어 약어를 풀어 쓰는 데서 멈추지 않는다. 무엇을 하는지, 무엇과 다른지,
왜 이 문제에서 필요한지 설명한다. 다른 미설명 용어로 정의하는 순환을 피한다.

완결된 사례의 입력·중간 상태·출력과 의미를 먼저 고정한다. 설명이 진행될수록
같은 사례에서 새로 이해하는 것이 생겨야 한다. 낯선 코드나 데이터 형식 전에 사람이
읽을 수 있는 값과 처리 과정을 설명한다. 가상 사례에는 그 상태를 밝힌다.

각 문단은 전제→작동 또는 관찰→독자에게 갖는 의미를 연결한다. 역할·조건을
나열한 표가 본문의 설명을 대신하지 않게 한다. 수치·도식에는 읽는 방법과 결론과의 관계를 쓴다.
학습 글에는 다른 조건으로 바꾸는 문제와 이유가 있는 풀이를 제공한다.
적용에 필요한 조건·한계는 본문에, 선택 심화와 개발 세부사항은 별도 학습 영역에 둔다.

문장 연결과 제목·요약의 실패 예시는 [집필·검토 예시](references/teaching-patterns.md)를 참고한다.
고정 목차·글자 수·문단 수를 충족시키기 위해 설명을 줄이거나 늘리지 않는다.

각 핵심 질문에 답하는 문단과 근거를 실제 지목한다. 답이 없으면 추가 조사하거나
범위를 정직하게 조정한다. 모든 주제의 결론을 ‘조건 확인·검증·기록’으로 끝내지 않는다.
그 주제 고유의 작동 원리, 실제 자료 해석, 계산 또는 업무 과정에서 새로 알게 되는 것이
있어야 한다. 번역투 교정은 누락된 지식을 대신하지 않는다.

## 제목과 요약은 본문 뒤에 작성

2026-10-09 음성 보고서의 제목·소개는 독립 에이전트 Pass 뒤에도 사용자가 거부했다.
그 판을 승인된 문체 견본으로 복제하지 않는다. [구체적인 실패와 수정 기준](references/substantive-review.md#첫-화면과-비교-기준의-회귀-사례)을 적용한다.

제목에는 대상이 무엇인지 알아볼 기술·주제 이름과 평이한 기능·문제·변화를 함께 담는다.
낯선 이름만 쓴 제목, ‘업무 흐름을 연결한다’ 같은 대상 없는 표현을 피한다.
기능을 과장하거나 관찰을 인과관계로 바꾸지 않는다.

요약은 글 밖에서 읽어도 독립적으로 이해되어야 한다. 이것은 무엇이고,
어떤 문제에 쓰이며, 무엇이 달라지고, 중요한 적용 조건은 무엇인지 설명한다.
본문의 B·호스트·문맥 같은 용어를 정의 없이 가져오지 않는다. 알 수 없는
축약어를 줄줄 나열하거나 ‘본문에서 배운다’는 소개 문구로 내용을 대신하지 않는다.

소개 문장은 독자가 하려는 일과 실제 대상부터 말한다. '선택 기준.', '오류 찾기.' 같은
명사형 조각으로 문장을 끝내지 않는다. 비교 대상은 같은 기준으로 구분하고, 구현 구조와
공급사 제품을 같은 종류의 행으로 섞지 않는다. 제목의 개수·비교·성능·실습 약속은
본문의 실제 내용과 일치시킨다. 속도·비용·개발 난이도의 우열은 필요한 근거 없이 약속하지 않는다.

## 두 가지 읽기로 검토

**제목·요약만 읽기:** 원고 밖 지식 없이 대상, 하는 일, 독자의 쓰임을 다시 설명한다.
답의 근거 문장을 지목한다. 본문을 읽어야만 알 수 있는 핵심이 있다면 제목·요약을 다시 쓴다.
이 단계의 검토 입력에서 본문을 실제로 제외한다. 이미 본문을 읽은 검토자가 빈칸을 메운
결과를 첫 화면만으로 이해한 증거로 사용하지 않는다. 소개 문구와 실제로 알게 된 정보를 구분한다.

**본문 따라 읽기:** 첫 등장 용어의 정의와 선행 개념을 확인하고, 사례의 시작부터
결과까지 각 단계의 이유를 추적한다. 다른 조건의 문제에도 본문만으로 답하고
설명 위치를 지목한다. 외부 지식으로 빈칸을 채워 통과시키지 않는다.

막힌 문장·잘못된 전제·누락 원문을 기록한 뒤 실제로 고친다. 형식 체크리스트를
통과했다고 학습 품질을 판정하지 않는다. 자체검토, 독립 에이전트 검토, 실제 독자 시험을
구분해 수행한 것만 보고한다. 이 스킬은 에이전트 위임이나 반복 실행을 자동 승인하지 않는다.

독립 검토가 사용자에게 승인된 작업에서는 검토자가 수정된 원고 자체를 읽고
문장·사례·근거 위치를 지목하게 한다. 지적을 실제 수정한 뒤 같은 결과물을 재검토한다.
에이전트의 사전 자문과 수정 후 판정, 자체검토와 실제 사람의 독해 시험을 구분한다.

근거·날짜 검토와 예제 실행·링크·렌더링 검증도 나눠 기록한다.
프로젝트의 기존 데이터 계약과 과거 판을 지킨다. 원고가 달라졌으면 기존 판을 덮어쓰지 않는다.
완료 시에는 적용 원고와 변경 이유, 실제 검증 범위, 남은 학습·실행 공백을 보여준다.
